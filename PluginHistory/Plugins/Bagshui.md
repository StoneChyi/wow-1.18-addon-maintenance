## 2026-10-11：背包、银行卡顿诊断

目的：用户反馈打开背包和银行明显延迟，要求先加入 debug 检验，再依据数据决定优化。此次只增加诊断，不修改刷新节奏、分类规则、排序和缓存策略。

主要文件：

- [Components/Performance.lua](../../Interface/AddOns/Bagshui/Components/Performance.lua)：独立诊断组件，默认关闭，手动开启后采样 60 秒自动停止。只保留本次登录的内存数据，不写 SavedVariables、不记录物品名、角色名、账号信息或事件参数。
- [Bagshui.xml](../../Interface/AddOns/Bagshui/Bagshui.xml)：在背包、银行、钥匙链组件创建完成后加载诊断组件，保持现有文件的 CRLF 与编码。
- [诊断回归检查](../../Tools/tests/test_bagshui_performance.py)：使用现有 Lua 5.1 测试运行时执行实际刷新、窗口打开和事件排队路径，耗时由可控时钟模拟。

诊断内容：按背包、银行、钥匙链统计刷新入口、格子扫描、分类索引、分类规则、排序、布局比较、窗口布局/按钮处理、背包栏、工具栏与物品提示扫描。每项列出次数、累计耗时、自身耗时、单次最大耗时、错误次数。记录实际刷新、跳过入口、排队请求与完整布局次数；保留最近 20 次打开，每次统计打开后 1 秒内的工作和下一帧等待，并记录采样期间全局最大帧间隔。

使用方法：

1. 更新文件后在游戏输入 `/reload`，或重新登录。
2. 输入 `/bs perf on` 开始新采样（会清空上一轮）。在 60 秒内反复打开/关闭背包，访问银行并反复打开；也可移动、拆分物品复现卡顿。
3. 输入 `/bs perf report` 停止采样并打开可复制报告，使用 Ctrl+A、Ctrl+C 复制报告。报告生成期间停止测量，避免污染样本。
4. `/bs perf off` 停止并保留数据；`/bs perf clear` 停止并清空；`/bs perf status` 查看状态。重新载入界面后默认关闭且旧采样不保留。

测量边界：使用客户端 `debugprofilestop`，不调用 `debugprofilestart` 重置共享计时器；缺少精确计时接口时拒绝启用，不以帧内可能不变化的 GetTime 冒充精确计时。包含子调用的耗时不能相加，“自身耗时”只扣除已测量子调用。全局帧间隔与下一帧等待还包含其他插件、游戏和系统工作，不能单独归因乾坤袋；窗口绘制项是 Lua 布局/按钮处理耗时，不代表 GPU 渲染时间。最近事件不是确定的因果归属。诊断自身有少量开销，数字不等于关闭诊断时的精确耗时。

实现约束：组件加载时安装稳定的转发函数，关闭时不读计时器、不分配统计记录、不运行诊断帧。开关不改变 Update 函数身份，保持已排队回调的去重与对应关系。启用时保留全部返回值（含 nil 空位）；原函数报错仍继续抛出。数据限于三类库存、固定阶段与最近 20 次打开。

关联功能：自动分类与整理、离线银行、停靠钥匙链、物品提示、冷却/锁定刷新及 Bagshui 事件队列。没有修改 OneBag、pfUI 或其他插件。

真实验证：19 组 Lua 5.1 行为检查通过；86 个 Bagshui Lua 文件语法通过；86 个 XML 加载路径存在性检查通过，主 XML 原有 CRLF 保留。检查覆盖默认关闭、真实打开流程的阶段计时、银行事件触发后的重复刷新、队列去重及开关时已有回调、返回值 nil 空位、异常原样传播、计时器复位、缺少计时接口、离线银行、1 秒观察范围、20 次记录上限、下一帧/全局间隔、60 秒自动停止与时长冻结、报告与清空、事件参数不记录、隐藏/阻塞刷新、停靠库存与重复打开。

以上为诊断初次实现时的受控模拟及静态检查；当时尚未取得游戏耗时报告、未实施性能优化。随后收到的用户采样与据此实施的修复记录见下。

## 2026-10-11：依据用户采样修复重复扫描和布局计算

用户反馈依据：v1 游戏内报告采样 16 秒，背包 144 格/108 占用格，13 次实际刷新产生 1404 次提示扫描（108×13）；银行 178 格/153 占用格，9 次实际刷新产生 1377 次提示扫描（153×9）。普通背包重复打开同步耗时约 81–86 ms，其中分类约 40–43 ms、提示扫描约 21–22 ms；银行打开后背包和银行通常各出现两次刷新。首次背包绘制单次最大 311.30 ms，全局最大帧间隔 1042 ms，后者不能全部归因本插件。原始报告由用户在本次维护聊天提供，不是修复后的性能验收。

目的：消除无变化物品的重复信息加载，复用有效的分类/布局结果，避免打开事件额外排队一轮刷新，保留真实物品变化的更新和现有操作行为。

主要文件和行为：

- [Inventory.Cache.lua](../../Interface/AddOns/Bagshui/Components/Inventory.Cache.lua)：锁定状态统一为 0/1，nil、false、0 都视作未锁定；锁定变化不再触发 GetItemInfo/完整提示加载。真实链接、数量、提示、充能和全量缓存变化仍使布局失效。保留原生提示充能解析及 SuperWoW 负数充能；空格保持 -1 充能标记，不参与原生充能提示重扫。
- 同一缓存文件保留未变化空格的堆叠代理、每次重建普通空格目标列表，避免轻量刷新清空堆叠数量或丢失换包目标。扫描未完成时返回等待状态，重试前清空本轮物品合计，避免部分扫描重试重复累计。
- [Inventory.Layout.lua](../../Interface/AddOns/Bagshui/Components/Inventory.Layout.lua)：内容和布局没有失效时跳过分类规则、排序与完整布局。打开时是否重新整理在实际扫描之后判断；已有“需要整理”状态仍在自动整理开启时生效。保留可见窗口的 dry run 行为，内容变化时保持现有物品位置，直至手动整理或重新打开。新增轻量按钮刷新，复用已有槽位更新数量、冷却、锁定灰色、变化标记和离线颜色。
- [Inventory.Ui.lua](../../Interface/AddOns/Bagshui/Components/Inventory.Ui.lua)：打开窗口不再无条件要求全量分类；编辑模式、展开空格、临时标题栏等几何变化仍触发完整布局。
- [Inventory.lua](../../Interface/AddOns/Bagshui/Components/Inventory.lua)：打开事件先请求扫描，由同步打开消耗该请求；扫描已完成且窗口可见时不再额外排队。已有独立回调不删除，后续真实 BAG_UPDATE 继续正常合并与刷新；缓存未完成时仍保留重试。
- [Bank.lua](../../Interface/AddOns/Bagshui/Components/Bank.lua)：银行在线/离线切换更新按钮显示，不单为状态切换要求全量布局；已打开的离线银行抵达银行时仍扫描实际内容。
- [Performance.lua](../../Interface/AddOns/Bagshui/Components/Performance.lua)：诊断更新为 v2，新增“物品按钮刷新”阶段。命令、60 秒自动停止和报告复制方式不变。
- [刷新回归检查](../../Tools/tests/test_bagshui_refresh.py) 与 [诊断回归检查](../../Tools/tests/test_bagshui_performance.py)：真实缓存、分类索引、排序协调、dry run、窗口打开、事件排队函数配合受控游戏 API/界面替身验证。

真实验证：35 组缓存/布局/事件行为检查和 19 组诊断行为检查通过；86 个 Lua 文件语法与 86 个 XML 加载路径检查通过。覆盖重复打开、nil/false/0/true/1 锁定、可见窗口位置保持、关闭自动整理、手动整理、冷却、物品替换/移除/移动/拆分、部分堆叠、容器交换/扩容、空格堆叠、专业包空格排除、两种充能来源、配方/角色/任务/装备/专业事件、分类/排序/设置失效、银行到达/离开/离线查看、已有独立回调、未缓存物品重试和编辑布局复位。

受控对照复现：使用维护提交 `a21e73c` 的修复前 UpdateCache，在三格、两件未锁定物品均未变化时仍发生 3 次物品信息加载和 2 次提示扫描；修复版同条件为 0 和 0。修复版稳定重新打开的工作量为 0 次物品信息加载、0 次分类、0 次完整布局，并保留按钮刷新。这些是模拟工作次数，不是客户端毫秒/FPS 收益。五个现有 Lua 文件的 BOM 状态与 CRLF 保持原样。

实施时的未确认事项：当时尚无修复后游戏内报告，不承诺具体耗时或提升比例；随后收到的复测结果见下。数量/充能、移动拆分、换包、离线银行等实际操作仍需客户端验收。没有改动其他插件或账号设置。

| 指标 | 修复前 v1 | 修复后 v2 |
| --- | --- | --- |
| 普通背包重复打开同步处理 | 约 81–86 ms | 约 5.2–6.3 ms；银行联动的一次为 7.21 ms |
| 银行重复打开同步处理 | 约 109–129 ms | 约 6.9–7.5 ms |

最近打开记录中的重复打开均为 1 次实际刷新、0 次完整布局、0 次分类/排序、0 次提示扫描。银行打开仍可能产生 2 次排队请求，但没有形成第二次实际刷新；排队计数不能当作执行次数。各测量阶段错误为 0，计时失效为 0。数据支持无变化时重复扫描、重复分类和重复布局已消除，重复打开耗时明显降低。两轮时长与操作次数不同，不以累计耗时或全局帧间隔计算插件的精确提升比例。

剩余开销集中在本轮首次完整布局：背包打开同步最大 164.38 ms，窗口布局/按钮处理最大 116.95 ms，分类 42.04 ms；银行首次打开同步 234.71 ms，其中窗口布局/按钮处理 171.56 ms、分类 57.06 ms。报告尚未细分窗口处理，不能确定其中各项初始化、皮肤或按钮创建的占比。后续若继续优化，应先细分首次完整布局与分类规则耗时。全局最大帧间隔由 v1 的 1042 ms 变为本轮 331 ms，仍含其他插件、游戏与系统开销，不能单独归因本修复。

验收边界：这份报告确认了重复打开路径的性能改善，不能仅凭零错误计数确认移动、拆分、换包、充能、离线银行等所有实际操作正确。首次打开仍有明显同步尖峰，未记录为完全解决。维护说明、索引和待补充清单同步更新，并通过维护记录检查；此次没有改动其他任务文件。

## 2026-10-11：继续优化规则运算与按钮布局

目的：用户同意实施进一步方案的前三项，并要求保持原有使用体验。此次在有效布局复用的基础上，减少规则参数处理、字符串匹配准备和完整布局中的重复按钮操作；没有实施按需创建装饰控件或改变预建按钮数量。

主要文件与行为：

- [Rules.lua](../../Interface/AddOns/Bagshui/Components/Rules.lua)：固定参数包装继续兼容旧版 Lua，将每次 50 次 `TableInsertNonNil` 调用改为直接写入复用参数表。保留跳过 nil、保留 false/空字符串、清除上一次参数、50 个参数限制及原有受保护执行路径。旧 Lua 清空数组后可能保留显式长度，直接写入后按需同步 `table.setn`，避免后续规则读到旧长度。
- 同一规则文件只复用文本转换结果，不缓存分类结论。每个物品求值会话最多复用 16 个原始字符串的小写结果，新会话清空；规则参数按原始字符串和匹配方式区分，最多 256 条，超过时清空，长度超过 2048 字节的参数不缓存。数量、任务、角色、动态参数、分类规则与搜索表达式仍实时求值；参数类型仍逐次验证。原有中文、字面字符、Lua 模式、大小写和本地化比较逻辑保留。
- [Inventory.Layout.lua](../../Interface/AddOns/Bagshui/Components/Inventory.Layout.lua) 与 [Ui.ItemButton.lua](../../Interface/AddOns/Bagshui/Components/Ui.ItemButton.lua)：同一次物品布局先调整按钮尺寸，随后绑定物品并统一更新颜色/徽标，避免在缩放过程中额外做一次完整显示处理。独立物品窗口、目录列表等未声明延后处理的调用仍立即更新颜色。父框架和缩放值相同时跳过重复设置；边框核对实际 `GetBackdrop()` 返回值，尺寸、贴图、背景、平铺和四边内缩发生变化时重新应用，外部替换边框也能恢复。物品绑定、贴图、数量、锁定、冷却和位置更新保留原有调用，刷新时机、分类优先级和排序策略不变。
- [规则与按钮回归检查](../../Tools/tests/test_bagshui_hotpaths.py)：执行真实规则、分类优先级、物品赋值与布局函数，与个人维护提交 `431fbc4` 的原函数比较显示结果；该提交不是官方原版。界面替身复用严格的 1.12 字体前置条件，未初始化或加载失败的字体不能直接写文本。

真实验证：新增 20 组规则/UI 行为检查通过，原有 19 组诊断及 35 组缓存/布局/事件检查通过，合计 74 组；86 个 Lua 文件语法、86 个 XML 加载路径检查通过。覆盖 nil/false/空字符串和参数上限、同一物品表修改、缓存上限、动态数量与参数、规则编辑、分类优先级/直接物品列表/职业规则、递归规则、搜索与错误处理、中文字面和 Lua 模式、锁定/充能/任务/可用性徽标、冷却开始结束、在线离线、编辑模式、皮肤边框/缩放变化、外部边框替换、独立调用即时着色、空格和物品替换。执行环境为 Lua 5.1，并依据 [Lua 5.0 官方手册的数组长度契约](https://www.lua.org/manual/5.0/manual.html#5.4)额外模拟 getn/setn/insert/remove 的显式长度，验证重复执行规则参数不丢失；这不是实际 1.12 客户端验收。三个现有 Lua 文件的 BOM 状态与 CRLF 保持原样；维护记录检查通过。

受控工作量对照：连续 100 次执行同一提示规则，小写转换和参数预处理均由 100 次变为 1 次，参数插入辅助调用由 5000 次变为 0 次。连续两次相同完整布局，颜色处理由 4 次变为 2 次，边框设置由 2 次变为 1 次，缩放和父框架设置各由 2 次变为 1 次；物品贴图、数量和冷却调用次数均保持为 2 次，最终显示状态与旧函数一致。这些是受控检查中的工作次数，不是客户端耗时或 FPS 提升承诺。

实施时的未确认事项：当时尚无本轮优化后的游戏内耗时和操作验收，前一节 v2 也不能作为本轮收益。随后收到的新采样见下。诊断仍为 v2，命令不变；移动拆分、充能、换包、搜索、皮肤显示与离线银行仍需实际操作验收。

## 2026-10-11：规则与按钮优化后的用户复测

来源：用户在维护聊天提供新的 v2 报告，采样 16.0 秒、2611 帧；背包 144 格/108 占用格，银行 178 格/153 占用格，与上一轮格数一致。本次只补充实测分析，没有继续修改刷新策略或插件代码。

| 指标 | 前一轮 v2 | 本轮 v2 |
| --- | --- | --- |
| 背包首次分类 | 42.04 ms | 20.18 ms |
| 银行首次分类 | 57.06 ms | 25.46 ms |
| 背包首次窗口布局/按钮处理 | 116.95 ms | 133.28 ms |
| 银行首次窗口布局/按钮处理 | 171.56 ms | 216.02 ms |
| 背包首次打开同步处理 | 164.38 ms | 158.72 ms |
