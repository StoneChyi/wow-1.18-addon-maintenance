## 第一部分：组队邀请

### 修改内容与原因

| 修改 | 原因 | 保留的行为 |
| --- | --- | --- |
| Group 与 StrangerDecline 使用一个组队邀请事件接收者 | 两个独立处理函数可能对同一邀请分别接受、拒绝，结果依赖事件次序 | 原模块独立开关、角色/账号范围、好友/公会、黑白名单、名字关键词、陌生人查询及55秒延迟 |
| 明确黑名单优先；白名单陌生人保留手动弹窗 | 白名单原本仅放行，但可能被 Group 陌生人拒绝分支覆盖 | 白名单中的好友/公会成员仍可由已启用的 Group 自动接受；临时暂停陌生人规则不绕过黑名单 |
| 延迟任务绑定一次邀请的代次、名字、弹窗和当前规则 | 原接受/拒绝使用不同定时ID，旧任务可能处理后来的邀请 | 新邀请、取消事件、手动响应、弹窗隐藏、组队变化、离开世界及模块停用使旧任务失效 |
| 等原生邀请框显示后再处理，执行前核对本地化模板 | 插件与原生UI事件次序不固定，不能猜测 popup.data 就是邀请者 | 无法确认来源时留给手动处理，不猜测、不接受其他弹窗 |
| Loner 的普通陌生人开关不再注销黑名单监听 | 原 setter 会将“黑名单独立生效”的事件一并撤销 | 公会邀请和签名规则保留；提示延迟改用已有 AceEvent，不依赖 C_Timer |
| Invite 与 invall 共用权限、容量与1秒内同目标去重 | 同一密语可能触发两次 InviteByName；原逻辑还可能先转团再发现对方不在允许名单 | 独立关键词、各自模块开关、允许名单、原踢人黑名单来源、转团选择；仅同目标短时合并，不是服务器节流方案 |
| invall 增加说话/大喊/密语、区域和升助理选项 | 原区域事件拼错、布尔比较无效，且升助理无独立控制；string.match 不属于原生 Lua5.0 | 默认不限区域保持旧实际行为；原模块启用时原升助理意愿保留，但仅团长执行，可单独关闭；没有自动开启模块 |
| 统一“邀请处理”“邀请玩家”两个原生页面 | 找设置时无需再来回切换四个相近模块 | 每组原选项对象/回调和独立启停不复制；原DB命名空间不迁移、不删除 |
| 组合页隐藏单独保存，旧ID跳转转入组合页 | 合并页面不能覆盖原模块隐藏、排序或独立工具箱设置 | 原 hiddenModules、moduleOrder、旧 navOrder ID 保留；自定义位置仍可调整，退出托管恢复原入口 |
| 修正邀请方向与白名单说明 | 原“自动接受好友邀请”实际是允许向好友发出邀请，容易设反 | 只改说明，不改变字段和原保存值；关键字大小写选项明确其实际作用 |

接收邀请的顺序为：已启用的黑名单拒绝 → 好友/公会自动接受（仅 Group 启用）→ 白名单放行 → 已启用的陌生人保护 → Group 陌生人拒绝 → 陌生人查询 → 手动处理。

### 可能存在的问题与后续方案

| 情况/边界 | 当前处理 | 后续验证或修改方案 |
| --- | --- | --- |
| 其他插件修改邀请框文字或结构 | 无法确认邀请者时取消自动动作，保留手动处理 | 若实际遇到，先收集该插件的弹窗构造路径，再增加明确的来源适配，不删除身份校验 |
| 公会名单刚登录尚未返回、好友/公会名单发生变化 | 保留原名单API，延迟执行前重评估；并未证明所有异步名单场景 | 实机核对首次登录邀请；若出现误判，增加名单就绪状态与待决策略，避免用空缓存直接判断陌生人 |
| 小队转团与服务器邀请响应异步 | 保留原同步转团后邀请方式，容量和权限已先检查 | 实机验证满小队邀请；若服务器需要等待，改为明确的队伍状态事件驱动单次重试，不无条件循环邀请 |
| 其他插件后加载时重写 AcceptGroup/DeclineGroup | 弹窗隐藏、取消事件和来源/代次检查仍提供保护 | 核查实际冲突插件的挂接链，再统一调用入口；不盲目反复覆盖全局函数 |
| invall 升助理消息目前按原中文系统消息匹配 | 原中文功能保留，并增加团长权限和独立开关 | 其他客户端语言若需要支持，再按原生本地化系统消息构造模式，避免匹配聊天文本 |
| 组合页隐藏与原常用菜单隐藏含义不同 | 组合页使用 pageHidden，子组选项保留旧常用菜单隐藏字段 | 用户实测恢复旧隐藏配置及排序；仅在明确需求下增加联动，避免自动覆写旧数据 |
| 用户实际邀请行为尚未验收 | 记录状态保留“待游戏验收” | 分别验证好友接受、黑名单拒绝、白名单手动、55秒中途手动响应、匹配密语一次邀请；不由维护代理向他人发测试邀请 |

## 第二部分：拾取确认与分配边界（2026-10-31）

### 修改内容与原因

| 修改 | 原因 | 配置与功能保留 |
| --- | --- | --- |
| pfUI 托管时统一处理绑定确认，LootBOP 只提供原启停与组队规则 | 两个事件处理者曾同时确认单人拾取 | 单人保留 pfUI autopickup 或 LootBOP 任一开启的意愿；组队仍要求 LootBOP 启用且 confirmInGroup 为真；没有迁移或覆盖原DB |
| 退出托管恢复 LootBOP 独立事件，pfUI 不重复处理同一确认 | 退出托管不能丢功能，也不能恢复双重确认 | pfUI 未加载时独立模块仍可用；切换执行者使旧队列失效 |
| “拾取绑定确认”页加入原 pfUI 单人开关和规则说明 | 相关设置分散，且旧“装绑”说明混淆拾取后绑定与装备后绑定 | 新入口写回同一个 C.loot.autopickup，原 pfUI 拾取页同步；模块原启停、角色/账号范围和组队开关保留 |
| 绑定确认按拾取会话、槽位、物品链接及实际弹窗核对 | 固定点击 Popup1 可能点错窗口；全局 confirming 标记会吞其他物品 | 不重造弹窗，不确认需求/贪婪或团长分配；每槽独立等待，失去来源时留手动 |
| 关闭、清槽、新拾取、离开世界、停用、托管切换和手动隐藏使旧任务失效 | 旧延迟不能处理新尸体或重新出现的弹窗 | 保留原 OnHide 脚本；确认API内部同步事件也不能擦掉新任务或关闭新弹窗 |
| AutoNeed 改用原 AceEvent 队列，核对 roll ID、选择、物品、剩余时间与当前规则 | 原代码依赖 C_Timer，且只检查 Popup1 类型而未核对实际掷骰 | 原31个四选项、分类、不选择=-1、默认值、个人物品与 CheckItem 原字节保留；取消和手动隐藏不再自动重确认 |
| pfUI 自动扫尸体让位于 SuperWoW | 当前角色存档同时开启 pfUI 单人拾取与 SuperWoW Shift 模式，pfUI 原循环绕过后者的手动意愿 | 保留 SuperWoW 三模式及 quickloot 可能反转的原行为；没有 SuperWoW 接管时，按 Shift 只抑制 pfUI 自己的扫尸体循环，不改客户端自身拾取行为 |
| SuperWoW 停用撤销轮询，模式切换复用框体，只在键态变化时写值 | 原停用只撤事件，OnUpdate 仍运行；每帧写 SetAutoloot 且反复创建框体 | 停用时仅在状态仍由本模块控制时恢复接管前值；停用期间编辑选项只保存；能力缺失或失败时停止驱动 |
| ShiQu 与 MasterLootRemind 保留独立职责 | 强制分配、分配提醒与绑定确认不是同一行为 | 未启用、停用或删除这些模块；没有让绑定确认自动选择需求或分配装备 |

## 第三部分：商人补货与批量购买（2026-10-31）

### 修改内容与原因

| 修改 | 原因 | 功能与配置保留 |
| --- | --- | --- |
| 自动补货与 Shift 批量购买开关加入商人服务；旧 Purchases 入口跳转同页 | 修理、售卖和购买需要在同一处查看，减少来回寻找 | 原三组补货选项直接复用原对象；原角色清单、数量、启停及角色/账号范围不迁移，批量开关仍写 C.global.buyemall |
| 补货数量明确为目标持有量；同一物品跨组三次出现取最高目标 | 原各组独立执行可能重复购买；商品每份多件时，购买份数与背包件数不能混用 | 三组清单和数量分别保留，原有物品不删除；按整份补足，可能超过目标不足一份 |
| 自动补货每次只发一份，等待背包增加与金钱扣除后再继续 | 本地背包和资金不是同步到账，连续发单可能重复或超预算 | 每次复核商品身份、价格、库存、资金和容量；只汇报已确认收到的数量 |
| 修理扣款确认后再售卖/补货；售卖未完成时购买等待 | 修理、卖灰和购买同时改变资金及背包，容易误判反馈 | 修理、自动售卖、自定义售卖、忽略名单和各自开关保留；自动补货关闭不影响原修理/售卖 |
| 补货目标与本次刚买到的物品临时排出售卖 | 自定义售卖名单和补货清单重叠时，可能买回后立即又卖掉 | 不改用户任何名单；商人会话关闭后清除临时保护，原手动逐件售卖仍可用；旧独立 Sell 也检查补货目标 |
