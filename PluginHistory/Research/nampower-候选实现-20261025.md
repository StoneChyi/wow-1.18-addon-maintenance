# nampower PSS 启动优化候选实现

日期：2026-10-25。状态：源码和 32 位候选已完成；现用 DLL 未替换，待游戏验收。

## 问题与范围

现用 nampower 4.6.1 的启动挂钩阶段多次约 3～4 秒。已核对本机二进制中的 Apply → VerifyPatchThreads → 全系统线程快照与遍历路径。参考源码启动时串行安装 59 个挂钩，而本机当时约有 6400 个系统线程。

本次将枚举替换为**每次新建的当前进程线程快照**，保留原当前线程排除、线程上下文检查、补丁目标范围判断和异常重试顺序。PSS API 不存在或失败时，先清理快照/marker、丢弃部分结果，再完整 Toolhelp 回退。没有长期缓存一次线程列表，没有移除校验，也没有新增全线程暂停。

实际代码见 [Tools/nampower](../../Tools/nampower/README.md)。源码准备只修改上游 `nampower/main.cpp` 的计时输出和 hadesmem `detail/patcher_aux.hpp` 的枚举接入；其余游戏逻辑文件保持下载源码原始字节。静态检查确认 59 个挂钩地址及顺序不变。

## 最终验证

所有验证均为独立程序或静态检查，没有加载候选 DLL 进入游戏、没有登录账号。

1. 真正 C++ 可注入 API 的 13 组边界测试全部通过：成功/新快照、保留退出线程元数据、五接口缺失、创建失败、marker 失败、遍历失败及部分结果、非法结果、清理错误、真实 bad_alloc 传播、非当前进程、Toolhelp 重试/错误、可选计时。
2. 启动计时开启/关闭测试通过：计时失败/倒退不下溢、嵌套会话恢复、异常退出记录、固定容量边界；开启和禁用均不改变校验操作。
3. 原生同机枚举测试通过：72 个固定线程、20 次同步新增/退出、5000 轮资源检查，句柄数 280 → 280。
4. 实际 hadesmem 校验函数的独立集成测试完成 3 组交替对照。**两边每组都执行 59 次 Verify、4248 次线程检查**，没有用减少检查数量换取提速。
5. 静态 PE 检查通过：两构建均为 x86 DLL，导出与现用版同为 `Load`；依赖均为 KERNEL32/USER32/CRYPT32，没有新增 VC 运行库 DLL；PSS 通过 GetProcAddress 动态获取，没有静态 PSS 导入。
6. 源码范围检查通过：挂钩地址/顺序 59 项一致；除 main.cpp 计时插入外，其他 nampower 游戏逻辑源文件无差异。

后者保留了真正的 hadesmem 线程校验路径。它只观察本测试进程的等待线程，不安装挂钩、不修改任何代码内存；运行线程上下文的原有限制没有因此消失。原路径没有单独测量枚举分项，日志 `enum_samples=0` 表示未测量，不是“枚举耗时为零”。

独立结果不代表游戏整个启动时间；也没有完成实际施法、事件、其他 DLL 或黑屏验收。详见[结构化检查结果](nampower-候选检查-20261025.json)。

## 审查与修正

- 修正了启动计时 QPC 失败/倒退时无符号下溢的问题。
- 改用每次独立构建目录并显式列举对象，避免静默复用旧 `.lib/.obj`。
- 将共享头与已准备源码内容绑定，并保存工具链/依赖/源码输入清单。
- 分开 DLL 与 IntegrationOnly 测试的清单，后者不覆盖旧 DLL 的构建来源。
- 原路径的分项计时以 `enum_samples=0` 明确未采样。
- 核心 PSS 集成审查未发现跳过原检查的实质回归。
