# nampower PSS 候选启动失败及撤回

日期：2026-10-25。结论：**候选未通过实际游戏启动，已恢复部署前旧 DLL。** 本次负面结果替代此前的“等待启动验收”，不能继续引用独立枚举速度作为游戏兼容性证明。

## 实际证据

用户在部署候选后提供 ERROR #132 截图。客户端生成 23:25:17 和 23:25:28 两份崩溃报告/转储，异常代码 `0xE06D7363`。

- 当时根目录 SHA256 为 `f226779fe49db61d1e87f16ad34a27188c06e5abf0ecc5f6df994c986c812bd7`，与本次 PSS 候选一致。
- 日志包含 MaintenanceBuild、`pss_enabled=1`，确认此次确实运行候选。
- 初始化第一个挂钩 `Script_SetCVar`，目标 `0x00488C10`，连续尝试 10 次均失败，随后没有正常完成初始化。
- 候选匹配 MAP 将栈定位到 `VerifyPatchThreads → PatchDetour::Apply → createHook → initHooks`。
- 两份转储中的实际异常对象均为 `boost::wrapexcept<hadesmem::Error>`；保存的抛错函数为 GetThreadContext，源行为 `thread_helpers.hpp:44`。
- 从 Boost 异常对象的 error_info 读取到 `GetThreadContext failed.`，以及保存的 Win32 错误码 **31（ERROR_GEN_FAILURE）**，不是仅凭 TEB LastError 或错误窗口猜测。
- 同一栈上的 PSS 诊断显示枚举成功、无回退与清理错误，共返回 31 个线程 ID。问题发生在后续逐线程取上下文校验阶段，不能称为已证明 PSS API 枚举本身失败。

失败线程未出现在各自转储的 28 条线程列表中；跨 WOW64 原生线程等解释尚待进一步证据，不能把它直接写成已证明的 UnitXP 保护或某个 DLL 冲突。

## 为什么已有独立验证不足

独立程序中的普通等待线程验证了枚举、资源释放及常规上下文检查，但没有覆盖此实际客户端及其已加载 DLL/驱动所形成的全部线程集合。不能把“保留相同检查数量”当成两种枚举在真实进程中的线程语义完全等价。

此外，现有 createHook 最终失败后抛异常，原启动回调未捕获整组初始化失败，导致异常退出。这条原有异常处理弱点已在前次源码审查中标明；本次实际失败使它成为已触发的故障链。日志中的 Unknown exception 是 e.what() 诊断不足，不能据此说它走了 catch(...)。

不采用跳过失败线程、删除安全校验或连续提供未经确认候选的办法规避问题。

原始材料只留本机忽略目录，不上传账号信息、内存转储或日志。候选及其 PDB/MAP 保留用于定位，并在本地候选目录标注实际启动失败。

从此前验证过的 `CodexBackups/nampower-20261025/current/nampower.dll` 恢复，替换后再次核对：

`1fe36ff8a421393116e6b58d801fa4dced35db59f1457136a79fce247142d4ec`

恢复后助手没有自动启动游戏。随后只读观察到 23:29 的旧版日志完成全部 hook 并注册 Glue 函数，但这不等同于用户已确认整体启动体验正常。

## 原先启动慢与用户的新线索

用户提出近期 UnitXP、wsloot 更新，以及 DXVK 三件套回退后可能存在配置遗留。原先启动卡顿与本候选新增的致命异常分开调查。

初步确认当前 d3d9、VanillaHelpers、dxvk.conf 与已记录回退版一致；当前图形日志实际加载 DXVK v2.5.3，旧 TexBridge.log 停在更新版运行时。缓存和 WTF 配置此前未整体回退，因此仍需逐项核对，而不能仅凭三文件恢复就宣称没有任何遗留。

UnitXP/wsloot 的外部改动保持原样，未为了撤回 nampower 候选而夹带回退。后续先完成版本、依赖和配置差异核对，再设计单变量对照，不将当前错误单独归罪于未验证组件。

后续只读核对已发现新版 wsloot 的硬件断点/线程调试链；版本、遗留与独立备份见[启动 DLL 核对报告](启动DLL版本与遗留核对-20261025.md)。这些核对没有改变现用 UnitXP/wsloot。
