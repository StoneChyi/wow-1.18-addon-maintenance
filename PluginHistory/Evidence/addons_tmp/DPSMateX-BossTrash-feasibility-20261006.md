# DPSMateX：Boss汇总与小怪时间范围可行性方案

检查日期：2026-10-06。依据当前目录中的 ShaguDPS、DPSMateX、DPSMateXExtend、DPSMateXExtendMore 和 DPSMateXInsights 源码。本文为设计方案，本次不修改插件运行代码。

## 1. 结论与推荐范围

可以实现。建议把“Boss汇总”和“小怪汇总”加入 DPSMateX 原有时间范围菜单，与“全程”“当前战斗”“历史战斗”并列。它们是统计范围，不是另两套伤害/治疗模块；切换范围后，当前统计模式、玩家筛选、宠物合并及原详情入口继续使用。

新增独立的战斗分类与汇总扩展，建议目录 `Interface/AddOns/DPSMateXEncounters`，依赖 DPSMateX，可选依赖 DPSMateXInsights。使用角色独立 SavedVariables `DPSMateXEncountersDB`，核心只接入战斗生命周期、事件观察、数据读取与菜单。分类不依赖新治疗或动作回放模块是否开启。

推荐默认：Boss汇总包含击杀及未击杀的Boss战；小怪汇总包含已识别为普通PvE战斗的累计数据。Boss战中的增援、小怪、治疗、吸收均计入整场Boss战。汇总周期为启用分类功能或最近一次清空数据之后。

当前根目录日志已确认Nampower 4.6.1，可使用现有GUID事件路线；分类仍在运行时检查接口。缺少单位分类能力时保留原范围，并将无法证明类型的战斗记为未分类，不要求升级才能使用DPSMateX原功能。

## 2. ShaguDPS的实际实现

| 项目 | 当前源码行为 | 参考价值 |
| --- | --- | --- |
| 小怪 | 脱战时，未标记 `is_boss_encounter` 的当前段通过专项合并器加入 `data.small_fight` | 分类在整场战斗结束后结算 |
| Boss识别 | `checkBossInvolvement()` 判断来源/目标是否为 `worldboss`；副本内直接标记，野外要求与玩家/队伍有关 | 按战斗事件判断，比单看当前选中目标稳定 |
| Boss汇总 | `GetBossSummaryDataRaw()` 对全程与小怪做递归相减 | 提供范围切换的使用方式，但不能直接套用到DPSMateX结构 |
| 时间 | 小怪时间累计 `last_fight_duration`；Boss时间为总战斗时间减小怪时间 | 每秒统计应采用选中范围的累计战斗时间 |
| Boss单场列表 | 需要观察到Boss死亡；同名Boss记录可被新记录覆盖 | 与Boss汇总不是同一种范围，列表并不包含所有失败尝试 |
| 最近战斗 | 有伤害/治疗且至少10秒，保留5场 | 是独立功能，此次不必同时改变DPSMateX历史数量规则 |
| 动作回放 | 全程、小怪、Boss汇总不提供回放，单场提供 | 汇总不应拼接成一条虚假的单场动作时间轴 |

因此，ShaguDPS的Boss汇总可能包括失败尝试，而Boss单场列表主要记录观察到死亡的战斗。推荐继承其汇总口径，不把Boss汇总限制为现存击杀历史记录之和。

## 3. DPSMateX现状与必须改动的地方

1. `GetMode()`、`GetModeByArr()` 只处理全程、当前和 `segmentN`。增加新范围时，两者必须一起接入，否则主栏与详情、附属统计会读取不同范围。
2. `GetModeName()`、报告标题及 Activity 模块有独立范围判断；必须统一，否则新增范围可能出现空标题、错误时间或索引错误。
3. `NewSegment()` 主要按照当前敌方承伤中数值最高的目标命名，再通过 `BabbleBoss:Contains()` 决定是否保存。最主要的受伤目标不一定是Boss；多目标战、增援和失败尝试均可能误判。
4. 当前 Babble-Boss 字典已经包含部分普通怪及增援名称，`Contains()` 代表“字典存在”，不能单独作为Boss名单使用。
5. `onlybossfights` 过滤历史保存，`datasegments` 限制历史数量。分类汇总必须在这些过滤/裁剪之外结算，否则小怪无法累计，旧Boss历史淘汰后汇总还会减少。
6. 分段一般在下一次进入战斗时保存上一场；脱战只把 `CombatState` 置为false。新增分类应在组队脱战时先结算，仍保留原单场保存流程，并通过唯一标记避免第二次结算。
7. 伤害数组同时包含次数、金额、最低值、最高值；光环包含应用/移除时间列表；死亡包含状态、记录和时间。普通递归加法/减法会破坏这些字段。
8. `ResetCurrentFight()` 会原地清空当前数据库；新汇总不能长期引用当前可变表。原 `CopyTable()` 是浅复制，新汇总的合并器必须独立创建/复制需要保存的叶节点。
9. 部分伤害/治疗详情直接读取光环范围，新增Insights又独立读取自己的分段。只修改核心主栏路由不够，需要一并适配这些入口。

源码位置：[核心范围读取](E:/1.18/Interface/AddOns/DPSMateX/DPSMateX.lua:719)、[分段保存及菜单](E:/1.18/Interface/AddOns/DPSMateX/DPSMateX_Options.lua:1639)、[组队战斗结束](E:/1.18/Interface/AddOns/DPSMateX/DPSMateX_DataBuilder.lua:2328)、[当前表清空](E:/1.18/Interface/AddOns/DPSMateX/DPSMateX.lua:1512)。

## 4. 界面与时间选择

保持现有标题栏的时间范围菜单和样式，新增两个条目：

| 范围 | 展示内容 | 时间口径 |
| --- | --- | --- |
| 全程 | 原有全程数据 | 保持原有行为 |
| 当前战斗 | 原有当前单场 | 当前/最近单场时间 |
| Boss汇总 | 本统计周期内所有已识别Boss战 | Boss战斗时长之和 |
| 小怪汇总 | 本统计周期内普通PvE战斗累计 | 小怪战斗时长之和 |
| 历史战斗 | 原有保存的单场战斗 | 该场时间 |

每个DPSMateX窗口独立选择范围。选择Boss汇总后可以继续选择伤害、DPS、治疗、治疗与实际吸收、成功施放等统计模式。无数据时主栏为空，沿用此前要求，不增加占位提示条。

详情使用原入口，不增加跨模块按钮。新治疗数据条继续仅显示数值和占比，不重新加入HPS。详情标题或现有副标题标明选中范围、累计场数和时间，避免将累计时长误解为一次Boss战。

本次不增加ShaguDPS式浮动按钮、不重做Boss单场列表、不改变历史场数设置。若以后需要“某一个Boss的所有尝试”或“某一天/某副本”，可基于分类元数据扩展，但不纳入本次默认范围。

## 5. 识别规则与战斗边界

### 5.1 分类

- 复用DPSMateX的队伍/宠物关系与 `CombatState`，由同一战斗协调器管理开始和结束，不新增全队轮询。
- 只观察与自己、队伍及其宠物有关的战斗事件。来源或目标为敌对 `worldboss` 时标记Boss；仅选中或经过Boss不触发分类。
- 对普通精英型副本首领、龟服自定义Boss，使用经过核对的“区域/副本＋名称”白名单；NPC ID仅在验证当前Nampower/GUID接口后作为辅助，不预设未确认API。
- Babble-Boss用于名称标准化，不能将其中所有名称自动当成Boss。
- 从伤害、承伤、普通攻击、有效战斗施法及死亡观察首领参与。分类观察不绑定原“死亡统计”模块开关，以免关闭该模块影响Boss统计。
- 首次确认Boss后整场归入Boss，并包含此前同场已发生的数据与Boss增援数据。普通PvE战斗归小怪。PvP、无法确认单位类型、重载中断等进入内部“未分类/其他”，避免把未知战斗强行算作小怪。
- 多Boss连续战斗记一个战斗ID及Boss集合；阶段空档、消失、假死、玩家自己脱战，不立刻结算。最终沿用队伍战斗结束规则。
- 单Boss可区分已观察击杀/未确认击杀；多Boss只有在遇敌集合与击杀条件足够明确时标记完成，不因为死了一个增援就声称整个遭遇获胜。

### 5.2 生命周期

使用持久化递增 `fightId` 标记整场战斗，手动分段使用 `sliceId`。同一个切片只累计一次。

开始 → 观察分类证据 → 队伍脱战 → 封口/处理待解析事件 → 分类合并 → 标记已结算 → 下一场开始时按原流程保存历史并清空当前。

手动分段仍属于同一个实际遭遇：若早期切片尚未见到Boss，先保存待定累计及元数据，后续识别Boss时按整个遭遇归类，避免前半段误算小怪。待定累计只保存合并后的统计，不保存无限切片副本。

待解析名字最多等待现有的短时上限；等待或补写必须绑定原 `fightId/sliceId`，不能写入下一场。未完成补写由受限日志记录。退出/重载中的开放战斗标记“中断”，保留已采集内容及分类证据；有明确Boss证据才进Boss，无法确认则进未分类，绝不续算离线时间。

## 6. 汇总存储与数据合并

推荐直接维护Boss、小怪和内部未分类累计，不通过现存历史反复重建，也不直接用原全程减小怪。

建议存储：

```text
DPSMateXEncountersDB
  version / sessionId / startedAt / nextFightId
  buckets
    boss / trash / unclassified
      duration / effectiveTimeByUser / fightCount / revision
      coreStatsByCategory
      insightsHealing / insightsCasts
      metadata
  currentEncounter
    fightId / sliceId / startedAt / classification / evidence
    settledSlices / pendingSummary
  boundedDebugLog
```

累计表不包含原始回放、无限死亡时间轴或每秒曲线。现存单场历史仍负责这些明细。

按数据结构提供专用合并器：

| 数据类型 | 合并规则 |
| --- | --- |
| 金额、次数、目标分布、受伤/施法来源 | 按对应键相加 |
| 最低值、最高值 | 忽略未采样0值后取min/max；不能相加 |
| 平均值、DPS/HPS、占比 | 保存分子和分母，展示时重新计算 |
| 用户ID、技能ID、学校、布尔状态、名称 | 保留身份或描述；不做加减 |
| 有效战斗时间 | 按玩家累计；继续支持原有活跃时间统计口径 |
| 新治疗与实际吸收 | 分别加总治疗、有效治疗、实际吸收、未知来源和排除量 |
| 新成功施放 | 按技能/来源/目标累计次数，保持同名技能展示合并 |
| 死亡 | 次数可累计；状态与每次死亡详情由专用适配器处理，不能把数值槽位全部相加 |
| 光环 | 次数/持续时间单独计算；跨场区间不直接叠在同一个0秒起点上 |
| 旧估算吸收、仇恨、失败、控制打破 | 逐模块检查状态/事件/计数语义后适配；不能套用伤害数组合并器 |
| 曲线、核对日志、动作回放 | 单场查询；汇总范围不伪造连续时间轴 |

例如，一场技能命中最低100，另一场最低200，汇总最低应为100，而不是300；平均伤害则应以总伤害/总命中次数计算。

分类数据守恒核对为“本功能采集的分类数据＝Boss＋小怪＋未分类”。原全程还可能包含安装前数据和战斗外治疗，不能强求其等于Boss＋小怪。原“全程”维持原口径，分类范围注明采集起点。

## 7. 兼容范围和实现次序

| 模块 | 可行性 | 建议处理 |
| --- | --- | --- |
| 伤害、DPS、承伤及相关目标/技能明细 | 高 | 首阶段专项数组合并并接入详情 |
| 总治疗、有效治疗、过量治疗、治疗承受 | 高 | 同步适配辅助数据库读取 |
| 治疗与实际吸收、成功施放 | 高 | Insights新增分类读取分支，沿用其独立数据口径 |
| 打断、驱散及细分类型、破甲 | 高 | 适配计数与目标/施法者嵌套结构 |
| 活跃时间 | 高，但有特殊路由 | 改造Activity的独立名称/时间选择逻辑 |
| 死亡、旧吸收、光环、触发、失败、控制打破 | 中，需要专用适配 | 第二阶段逐项接入并验证详情；未适配前明确不支持新范围 |
| 仇恨/TPS | 中，状态与历史语义不同 | 保持原实时/单场用途；分类汇总不承诺实时仇恨排序 |
| 动作回放及单场事件曲线 | 汇总范围不适用 | 进入这些模式时沿用原习惯切至当前或指定历史单场 |

适配状态由注册表声明。未适配模块不能悄悄展示全程数据，也不能导致整个窗口报错；切换到不适用模块时选择原有效范围，并在已有提示位置解释一次，主栏不新增假数据。

最后发布前应完成核心伤害/治疗、新增治疗吸收/施放、打断驱散和Activity支持；高级模块有明确支持范围表和测试结果。不能把“菜单出现”当作所有模块已经兼容。

## 8. 接入点与代码组织

建议新扩展拆为 `Encounter.lua`（分类和生命周期）、`Merge.lua`（专项合并）、`Views.lua`（统一读取）、`Menu.lua`（原菜单条目）、`Debug.lua`（受限核对）。

- DPSMateX.lua：`GetMode`、`GetModeByArr`、`GetModeName`、初始化/清空/当前段重置接入。
- DPSMateX_DataBuilder.lua：入战、组队脱战和现有事件转发增加轻量观察；保留原采集器，不复制一套伤害/治疗事件解析。
- DPSMateX_Options.lua：初始及重建时间菜单都加入 `bossall` / `trashall`；调整 `ToggleSegment` 的更新标记；历史保存/移除同步分类元数据。
- 原伤害/治疗详情：统一读取光环及辅助统计范围；汇总不执行单场事件相关性分析。
- DPSMateXExtend/ExtendMore：按注册表声明专项合并器；Activity增加累计有效时间读取。
- DPSMateXInsights：分类存储/读取治疗和施放汇总；回放继续只保留单场。

累计范围视图可按 `revision＋窗口筛选` 缓存。进行中战斗采用“已结算累计＋当前待定片段”的只读视图，最多按原主栏约1秒刷新合成一次；当前由小怪待定变为Boss时，移动的是视图归属而非反复扣加持久表。脱战后只有一次正式累计。

## 9. 历史、清空和迁移

- 历史数量上限、仅保存Boss历史、删除某场历史，均不改变本统计周期已累计的Boss/小怪总量。这与原全程删除历史后仍保留累计的行为一致。
- “清空数据”同步清空分类累计和当前结算标记，更新统计起点；战斗中清空只统计清空之后的数据，防止旧切片重新累计。
- 启用前的全程缺少分类证据，不自动伪造分类数据。旧历史保留，默认只新增以后采集的分类统计。
- 不默认把旧历史加进分类累计：有限历史并不完整，按名称回填还可能把增援误当Boss。
- 更换队伍、换地图不自动替用户清空统计；延续现有清空/询问设置。当前开放战斗在跨区域中断时单独标记，不能把两张地图的战斗连在一起。
- 数据带版本号，模式开关和已有Insights设置保留；新扩展关闭后原全程/当前/历史继续使用。

## 10. 资源控制

1. 战斗事件只做相关性筛选和小规模分类证据记录，不新增全技能扫描、全队光环扫描或更高频率轮询。
2. 专项合并只在脱战/手动分段封口时执行。避免每次菜单刷新都递归处理全程和所有历史。
3. 两个主要累计表只保存统计摘要，不保存新的逐事件副本；原回放继续沿用每人500条、每场8000条上限。
4. 当前范围合成只对正在查看的模块进行，缓存有容量上限，复用原主栏刷新频率；详情只在打开/交互时整理。
5. 多Boss证据、GUID判断缓存和调试日志均设上限。长战或超大合并工作可在脱战后分帧处理，合并完成后原子切换视图，不能让UI读到半成品。
6. 长期摘要的不同目标/技能键仍可能增长，单纯取消逐事件记录不等于内存无限安全。建议初始限制为每个累计范围最多1万条目标细节节点、每玩家每统计类型最多64个目标、分类GUID缓存256项、调试日志200条、合成视图缓存最多4份。超限目标并入“其他”，保留金额/次数及技能汇总，并在详情标明细节已收敛；主汇总统计不因细节裁剪变小。这些是建议的初始预算，发布前依据压力测试调整，不将节点数量当作固定内存承诺。
7. 不额外强制垃圾回收。以40人、多目标、多个窗口、连续多小时数据检验CPU、保留内存和保存体积，再选择默认预算。

可以控制新增开销，但不能在尚未进行游戏实测时承诺绝对零资源消耗。

## 11. 验收标准

- 先小怪后Boss、Boss失败再击杀、多Boss/增援战、最高伤害目标不是Boss、野外旁观Boss、普通精英Boss及自定义白名单均正确分类。
- 死亡统计关闭仍识别Boss；队友拉怪、宠物攻击、治疗起战、全吸收伤害与未命中事件不漏掉相关战斗。
- 进出战、队伍短暂空档、假死/消失、Boss死亡后增援未脱战、手动分段、战斗中清空/退出/重载不重复结算，离线时间不增加。
- 历史仅Boss/只保留1场/自动裁剪/手动删除后，分类累计不减少；清空时分类一起归零。
- 两场技能最低/最高、平均、暴击比例、玩家活跃时间、目标分布及伤害/治疗汇总正确，且不修改原始单场和全程表。
- 主栏、玩家/技能/目标详情、报告、对比和Activity读取同一个时间范围；多窗口独立选择，无数据不生成占位条。
- 新治疗仍无额外HPS数据条；图标缓存、同名技能合并、未知吸收核对继续有效；动作回放保持单场。
- 40人长战和数万事件模拟、频繁切换菜单与历史、多个详情窗口、超预算目标细节收敛测试通过。
- 最后游戏内核对真实NPC分类、战斗结束时序、帧率、内存和SavedVariables体积；不把离线模拟耗时当作真实客户端帧率。

## 12. 推荐实施顺序

第一步：独立分类协调器、两个时间菜单和专项伤害/治疗汇总；打通核心读取、辅助读取和报告，测试结算唯一性与历史独立性。

第二步：接入Insights治疗/吸收与成功施放、打断/驱散、Activity及对应详情；保留用户既定UI样式和无数据行为。

第三步：高级死亡/光环/旧吸收等逐模块适配；统一“不适用范围”的处理，不将实时状态伪装成累计统计。

第四步：运行资源压力测试、旧数据迁移/开关回归及真实游戏验收，确定摘要容量默认预算。全程与当前统计须与改造前一致，新增分类汇总有明确采集起点及可核对的边界。

以上是推荐方案；此次仅检查源码和提交方案，没有修改运行代码。
