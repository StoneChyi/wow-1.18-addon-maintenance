# DPSMateX 结合 ShaguDPS 的可行性检查

检查日期：2026-10-06。检查对象为当前 E:/1.18 中的插件代码。

结论：三项功能可以实现。适合新增一个依赖 DPSMateX 的扩展插件，将采集、保存、模块展示和详情页分开。借鉴 ShaguDPS 的事件来源和数据字段，修正其吸收归属及施放计数问题。此次未修改插件功能代码；完成了静态检查和吸收分配函数的模拟验证，尚未在游戏内验证运行时事件版本、先后顺序与性能。

## 2. 护盾吸收并入治疗

### 可行的采集链路

1. 从 AURA_CAST 取得施法者 GUID、目标 GUID、技能 ID，维护护盾生命周期。
2. 从法术伤害 mitigationStr、平砍 totalAbsorb、环境伤害 absorb 读取本次实际吸收量。
3. 结合护盾生效、刷新、移除、伤害学校等信息判断归属。
4. 将吸收单独保存，展示时与治疗汇总；一笔吸收只入账一次。

当前 DPSMateX 的 Nampower 分支中，AuraCastX 的 AwaitingAbsorbConfirmation 和 AuraChangedX 的 UnregisterAbsorb 调用被注释；伤害入口主要写入 Temp.broken。不能仅打开原“治疗和吸收”模式就得到 ShaguDPS 式完整采集链路。

### ShaguDPS 可以参考的部分

它将实际发生的吸收计入治疗总量和有效治疗，吸收没有过量治疗。吸收时记录施法者、护盾技能和受保护目标，适合转换成 DPSMateX 的技能/目标详情数据。

### 不宜直接沿用的部分

- processAbsorb 接收 spellSchool，但没有用它筛选护盾，按数组从后向前分配。
- shieldMaxAbsorb 是按中文技能名写死的容量，未考虑技能等级、加成和服务器差异。
- onBuffAdded 无法确认施法者时会用受保护者 GUID 作为施法者，存在归属错误风险。
- 多护盾共存时，事件通常只提供本次吸收总量；总量与具体护盾/施法者的归属精度应分别处理。

调用当前源码中实际的 processAbsorb 函数，模拟游戏 API 后得到：

| 输入 | 当前函数输出 | 含义 |
| --- | --- | --- |
| 冰霜伤害吸收 100，缓存里仅有火焰结界 | 给火焰结界施法者记 100 | 没有检查伤害学校 |
| 吸收事件 1500，缓存护盾容量 1083 | 仅记 1083 | 固定容量可能截断实际事件总量 |
| 两个护盾，吸收 100 | 全部给数组中后加入的施法者 | 依赖缓存顺序，不能据此证明实际归属 |

推荐新模块保存三个基础值：治疗总量、有效治疗、实际吸收。可展示“总治疗＋吸收”和“有效治疗＋吸收”两种口径；默认使用有效治疗＋吸收更适合贡献对比。两者均应在详情中拆开。原治疗表保持原来的含义，避免合计模块重复加吸收。

无法确定来源的吸收保留到“来源未知”数据中，不能随意归给受保护者；多人/多盾场景的推断需要记录依据，便于核对。需要明确自用护盾、药水吸收、物品触发是否计入合计，可参考 ShaguDPS 的范围提供分类筛选。

## 3. 技能施放统计

新增独立数据表，主要以 SPELL_GO_SELF/OTHER 记录成功施放，一次成功施放计一次。伤害命中次数、持续伤害跳数和多目标治疗次数应单独统计。

当前 DPSMateX 的 SpellGoX 能提供施法者、技能和目标，但将原事件的 itemId 等字段丢弃，且 OnSpellCast 主要处理破甲追踪、驱散及广播。因此需要在入口保留更多原始信息，并扩展宠物归属处理。

建议字段：施法者、宠物主人、技能 ID、物品 ID、来源类型、目标类型、成功次数、目标分布。普通攻击可供动作回放使用，在技能施放统计里作为可选分类，避免与原 Casts 的排除口径混淆。

ShaguDPS 的 onSpellGo 和非周期性 onSpellHealBySelf/Other 都会增加 spellcast。若一次治疗同时触发两类事件，就有重复计数风险；群体治疗更不能按治疗目标数计算施放数。新模块需采用明确的主事件来源，补偿路径仅在确实缺失主事件时使用并去重。

## 4. 动作回放

按战斗保存动作时间轴，适合包含：相对时间、序号、施法者、技能、来源、目标 GUID/名称、友敌关系，以及自己/目标死亡事件。技能施放与回放共享标准化采集结果，减少两套代码产生统计差异。

回放要服从 DPSMateX 的战斗边界。当前 CombatState 是 DataBuilder.lua 的局部变量；战斗结束由 OnUpdate 检查，不宜单独按 PLAYER_REGEN 事件建立另一套时间基准。CreateSegment 当前按固定列表保存数据库，ResetCurrentFight 也按固定列表重置，需要在这些位置加入新模块的保存和重置入口。

建议支持当前与历史单场战斗，避免在全程视图把不同战斗从零开始的相对时间混在一起。采用每场及全局事件上限、分页和延迟刷新；回放单独保存且不与可变缓存共享表引用。旧历史中缺失的新数据应显示“该战斗未采集此模块”，不能伪造为真实的零。

## 5. 与 DPSMateX 相同风格的详情界面

可以复用现有的深色背景、Tooltip 边框、字体、职业颜色、技能图标、列表交互、缩放设置、图表库及对比入口。不同数据需要各自的布局：

| 模块 | 详情布局建议 |
| --- | --- |
| 治疗＋实际吸收 | 顶部总量/有效治疗/吸收/HPS；按技能和目标展开；治疗与吸收占比图；随时间的贡献曲线；来源未知吸收与原始事件核对入口。 |
| 技能施放 | 技能图标、成功次数、占比、来源和目标分布；玩家/宠物/物品筛选；同技能两人对比。命中次数作为另外的字段。 |
| 动作回放 | 时间、技能、来源、目标的滚动表；技能/目标/时间区间筛选；死亡标记；同一时刻按采集序号稳定排序。 |

现有 HealingAndAbsorbs 详情页已经提供技能/目标视图、饼图、折线、堆叠图和对比；Casts 详情页提供技能图标/次数列表。可以复用外观与交互方式，但不能将旧 EvalTable 直接接到新数据库，因为结构不同。

## 6. 建议的模块边界与实施顺序

一个新扩展插件依赖 DPSMateX，提供独立采集层和三个展示模块；运行时无需启用 ShaguDPS。

1. 实际吸收采集与治疗合计：先确定护盾范围、口径、来源未知的处理，再实现详情与核对。
2. 成功施放：建立唯一计数入口，覆盖伤害、治疗、群体技能、未命中、宠物和物品。
3. 动作回放：复用施放数据，补平砍和死亡事件，接入分段及独立持久化。

少量 DPSMateX 核心改动用于事件分发、模块启用条件、战斗开始/结束信号、初始化/保存/重置接口；主要功能和 UI 位于新扩展内。直接覆盖共享 OnEvent 或每个模块各自重复解析事件，不利于稳定性和排错。

## 7. 实施前与游戏内验证

- 当前 ShaguDPS 要求 Nampower >= 4.5；DPSMateX 的判定仅从 3.4 起接受。新模块应按实际 API/事件能力检测，运行时版本本次尚未确认。
- 验证事件先后顺序：战前套盾、刷新、移除、全额吸收、多个护盾、施法与目标死亡相邻时刻。
- 验证计数：群体技能一次施放、多次命中；HoT/DoT 一次施放、多次跳数；治疗施放事件与治疗结果同时出现；宠物和物品触发。
- 验证生命周期：新战斗、手工分段、历史删除、整体重置、战斗中 reload、旧存档与新字段迁移。
- 核对约束：吸收事件总量 = 已归属量 + 来源未知量；合计值 = 对应治疗量 + 吸收量；汇总与详情一致。
- 提供模块独立开关、限量调试日志和数据版本号，记录事件时间、GUID、技能 ID、归属依据和去重结果；限制内存与文件增长。

以上是代码层面的可行性结论。具体多人护盾归属精度和有效治疗的事件时序，需要游戏内日志才能最终确认。
