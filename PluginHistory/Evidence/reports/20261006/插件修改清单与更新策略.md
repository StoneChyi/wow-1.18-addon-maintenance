## 推荐：先排除更新，再逐批合并

1. 完整退出所有游戏客户端，确保配置写入磁盘。把 Interface/AddOns 和 WTF 备份到游戏安装目录之外的独立备份目录，保留日期，不覆盖上一份。AddOns 保存代码，WTF 保存角色设置、预设、宏等，两者都需要。
2. 将这 16 个目录列为个人修改保护清单。若更新器明确支持“忽略/排除/冻结”，按清单设置，并确认对整包更新也生效。尚未检查更新器界面，不能保证存在或适用该功能。
3. 若没有可靠排除功能，把新整合包先解压到独立暂存目录；只复制未保护的插件。会自动清空 AddOns 再重建的更新方式还可能删除新增模块，不能仅靠“不覆盖同名文件”保留扩展。
4. 保护目录先保留当前完整版本；需要新版修复时，对比合并后再更新。短期冻结会推迟上游修复，长期应持续合并，不能无限期认为旧版都兼容。
5. 完整启动游戏，检查新增模块启用状态、Lua 报错、预设切换及位置保存。在确认更新正常之前保留更新前的 AddOns 与 WTF。

## 长期保留改动，同时接收新版

每次保留三份：A=修改所基于的原整合包版本；B=个人修改版；C=新的原整合包版本。比较 A→B 的个人改动与 A→C 的上游改动，生成合并后的 D。双方修改同一处时停下来审查，不自动用旧文件覆盖新文件。

可用本地 Git 分别保存上游版本及个人修改，采用三方合并、标记日期和修改目的。不必上传代码或 WTF 到网络。Git 能合并文本变更和标记冲突，但没有文本冲突仍需验证游戏行为。官方说明：https://git-scm.com/docs/git-merge

当前散落的备份往往是“某一轮修改前”的中间版本，不保证是当天所有改动前的干净原版。建立完整原版基线时，需要保留对应旧整合包并先核对；不能把任意 .original 或旧 ZIP 当成统一基线。已有增量补丁也不能不分顺序全部重放，或在新版本强制套用。

未来尽量把能通过稳定接口挂接的外观和扩展功能放进独立的个人插件；仍需改动主插件内部的循环、目标筛选、加载流程和采集接口时，保留小范围差异及接入点记录。DPSMateX 现有两个独立扩展并非完全脱离主插件修改。

## 不适合作为主要保护方式

- 只备份 WTF：恢复不了修改后的 Lua、XML、TOC。
- 只改文件夹名或 TOC 版本号：可能影响依赖/资源路径，也不能保证更新器不会覆盖。
- 只设只读：不等于更新排除规则，可能让更新部分失败。
- 每次新版安装后无条件覆盖回旧 Lua：会丢失上游修复，可能与新 XML、TOC 或配套模块不兼容。完整旧目录仅适合明确选择回退时使用。
