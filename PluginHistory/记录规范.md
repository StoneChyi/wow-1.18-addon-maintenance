# 插件修改记录规范

[返回总入口](README.md) · [插件分类](Plugins/README.md) · [记录模板](记录模板.md)

## 分类

1. **没有变化的插件**：现有依据没有确认本插件本体发生版本迭代或文件修改。仅来源补充、未实施的差异核对、其他插件的皮肤适配不算本体变化。不是官方原版认证，也不推断历史从未修改。
2. **经过版本迭代或修改的插件**：有实际版本更新、自行修改、新增、回退或文件差异依据；作者归属不明可如实备注，不据此退回第一类。
3. **DLL 等其他组件**：记录放在 `Runtime/`，不计入插件数量。关联插件互相链接即可，不复制整份历史。

原始记录暂不删除。DLL 等组件的旧 Plugins 页面保留为原始副本，当前记录维护 Runtime 页面；旧副本不重复计入分类与时间条数。全部整理完成后的清理须另行确认。

分类写入 maintenance-index.json 的 history_group（unchanged / modified）。原有 status 只描述证据与个人修改归属，不再决定导航分类；初始化 addons 与后来 added_addons 保持分开。UnitXP_SP3_Addon 的 2026-10-25 记录明确插件17个文件未变，实际 DLL 恢复另记，不能把 DLL 更新写成本插件修改。

## 每个插件的页面

- 插件概况与当前维护摘要保持简短。
- **逐次修改记录**是主体，按日期及当日编号倒序。保留原有编号、日期、证据与回退关系，不抹掉失败或已替代的历史。
- **目前存在的问题**是可选章节：只记录有真实依据且尚未解决的问题，注明最近状态和依据。历史故障已修复而未完成游戏验收时，不直接称仍在发生。
- **进一步优化方案**是可选章节：只记录已经提出且仍适用的方案；不能因模板有这一节而补造计划，已实施方案移回历史语境。
- **早期历史汇总与维护依据**保留日期不明的真实记录，折叠展示。旧说明里的“当前”“待补充”不是当前任务；不要机械复制到问题或优化章节。

没有问题或方案时直接省略相应章节，不填“暂无”“待补充”占位列表。未变化插件不制造修改条目。

## 时间条目

标题 `### YYYY-MM-DD｜说明`，稳定锚点 `change-插件名-YYYYMMDD-序号`。编号按当天递增，不能重排旧编号。日期不明保留早期汇总，后续补充时区分实际发生日与确认日。

条目写清原因、实际变化、相关文件、真实检查/游戏验收结果和证据；有关联或替代关系时再写。来源补充、方案及未部署核对必须明确未修改代码，不能当成已实施成果。

兼容既有记录类型：修改、更新合并、实测反馈、方案、来源补充、差异核对、停用、范围确认。游戏验收使用：待游戏验收、用户实测（限本条范围）、不适用（说明或停用记录）。模拟检查不等于游戏验收。

对应提交使用真实完整链接；与代码同次提交的新条目写“随本条记录一并提交（见本页 Git 历史）”，不伪造提交号或时间。

## 更新与检查

编辑插件页，必要时更新分类；运行：

```text
python Tools/plugin_history.py build
python Tools/plugin_history.py check
python Tools/check_plugin_notes.py
```

索引由这些页面和维护清单生成，不手工复制一份待补充名单。新增组件更新 runtime_components 的 Runtime 路径。保持原编码/BOM/换行，原始 Evidence、初始化清单和基线不改写。提交、同步仍遵循仓库已有维护流程及本次任务授权范围。
