## BrainwasherPro + Outfitter 换装问题修复
- 问题：使用 BrainwasherPro 切换天赋时，Outfitter 套装切换经常出现头部装备未换，且装备列表里同时勾选 2 个配置。
- 根因：BrainwasherPro 的 `SwitchOutfitterSet` 调用 `Outfitter_WearOutfit(targetOutfit)` 时未传入分类 ID，导致 Outfitter 不会按完整/混搭规则清理套装栈，旧套装仍留在栈中；列表勾选基于栈内存在与否，因此会同时显示多个勾选；未覆盖的槽位（如头部）继续沿用旧套装。
- 修复（BrainwasherPro.lua）：
  - 查找套装时同时记录其所属 `category`，调用 `Outfitter_WearOutfit(targetOutfit, targetCategory)`。
  - 为 `CheckAndSwitchItemSet` 增加 0.5 秒检查节流，避免每帧调用。
  - 在 `OnTalentLoadComplete` 中同步重置套装检查计时器，使切换后能立即生效。
- 备份：BrainwasherPro/backup/BrainwasherPro.lua.20260826_210535

## （续）头部不换的真正根因：光标抢占，而非银行
- 用户回传实测聊天日志：前面 5 次切换（47234↔47228 来回）头部**都能正常换**，证明两个头部都在背包、Outfitter 换装本身没问题；只有"猛切天赋来回"时才连续两次头部没换并卡死。
- 推翻了上一版"多半在银行"的判断——银行取不到的话前面一次都换不了。
- 真正根因：`Outfitter_ForceEquipNow` 换头部用**背包取装**（`PickupContainerItem`+`EquipCursorItem`），共用一个光标。1.3 秒内连续两次 `WearOutfit+ForceEquipNow` 时，上一次换装光标动作未落地，后一次抢占光标，把前一次的头部换装弄丢（表现就是连续两次卡死）。
- 修复（BrainwasherPro.lua 第 3 轮）：换装**串行化**——新增 `ABP_OUTFIT_EQUIP_GAP=1.3s` / `lastWearTime` / `equipInFlight`；`CheckAndSwitchItemSet` 在上次换装仍"飞行中"且未超 1.3s 时直接 return 不发新换装；`SwitchOutfitterSet` 下发后置 `equipInFlight=true`；`BrainwasherPro_VerifyHead` 校验成功（头部 itemID 对上）才置 `equipInFlight=false` 解锁。失败提示改为"间隔太短抢光标 / 头部在银行"两种可能。
- 校验窗口从 0.6s 提到 0.8s，避免慢服务器误报。
- 备份：BrainwasherPro/backup/BrainwasherPro.lua.20260826_222800
- 经验：WoW 背包取装依赖光标，任何“连续自动换装”都必须串行化 + 最小间隔，否则光标冲突丢槽位。

## （续2）头部不换的真正根因：Outfitter 物品缓存陈旧
- 用户回传第二轮日志：上一次换装（暗牧AOE→47234）已被校验确认成功，但切回治疗（目标 47228）时头部仍停在 47234。说明不是光标冲突（串行化没拦住），而是 `WearOutfit` 实际执行了但头部被跳过。
- 真根因：Outfitter 的 `OutfitterItemList_GetEquippableItems` 缓存 `gOutfitter_EquippableItems`（Outfitter.lua:6072），只有 `NeedsUpdate` 为真才重扫；而 `ExecuteEquipmentChangeList` 里的 `OutfitterItemList_SwapLocationWithInventorySlot`（6172）是**空函数**，换装后缓存不主动更新，只能靠 BAG_UPDATE/PLAYER_EQUIPMENT_CHANGED 事件失效。猛切天赋时这些事件延迟/合并，`NeedsUpdate` 偶尔没置真 → 缓存停在旧状态（还记着“头部=47228”）→ `BuildEquipmentChangeList`（3244-3254）误判目标头部“已在头上”而从换装清单里移除跳过 → 头部卡住。
- 修复（BrainwasherPro.lua 第 4 轮，备份 20260826_224000）：
  1. 每次 `WearOutfit` 前强制 `gOutfitter_EquippableItems.NeedsUpdate = true`，逼 Outfitter 重扫背包/装备，拿到真实状态，头部不再被误跳过（根治）。
  2. 头部换装校验失败时，自动重试一次（0.6s 后重发 `WearOutfit`，同样强制刷新缓存），`headRetryConsumed` 限单次避免无限重试（兜底）。
- 经验：调用 Outfitter `WearOutfit` 前务必把 `gOutfitter_EquippableItems.NeedsUpdate` 置真，否则连续换装会出现“误以为已装备而跳过”的诡异丢槽。

## （续3）重试 bug + 改用“直接强制戴头”兜底（最终可靠方案）
- 用户回传第 3 轮日志：初始换装（47234→47228）**仍失败**，且重试报错「未找到Outfitter套装: 疫医布帽」——暴露两个 bug：
  1. 重试逻辑把**头部物品名「疫医布帽」**当成了**套装名「治疗」**去 `SwitchOutfitterSet`，自然找不到套装（代码笔误：`headRetryPending.name` 存的是头部物品名）。
  2. 第 4 轮加的 `NeedsUpdate=true` 强制刷新在实测中并未稳定生效（Outfitter 内部时序太绕），头部仍被漏换。
- 方向性失效（暗牧恒成功、治疗恒失败）印证：缓存一旦被卡在“头部=47228”就**无法自愈**——因为 47234 成功那次也不会把缓存纠正回 47228，于是每次切治疗都误判“已就位”而跳过，形成死锁。
- **最终方案（BrainwasherPro.lua 第 5 轮，备份 20260826_230000）**：彻底弃用脆弱的 Outfitter 缓存刷新 + 重试队列，改为**在延迟校验时直接绕过 Outfitter 强制戴头**：
  - 新增 `BrainwasherPro_ForceEquipHead(pTargetCode)`：0.8s 校验发现头部 itemID 不符时，自己 `GetContainerItemLink` 扫描背包(0-4)按 itemID 找目标头部，`PickupContainerItem`+`EquipCursorItem(HeadSlotID)` 直接戴上，完全不依赖 Outfitter 内部状态；背包找不到返回 false → 报“目标头部在银行/仓库”。
  - `BrainwasherPro_VerifyHead` 改写：对上则报成功；不对则调 `ForceEquipHead` 兜底；仍失败才提示银行。无论成败都 `equipInFlight=false` 解锁。
  - 删除 `headRetryPending`/`headRetryConsumed`/`pIsRetry` 整条重试机制及相关 OnUpdate 代码。
- 关键结论：Outfitter 联动换装时，最可靠的做法是**自己扫描背包+`PickupContainerItem`+`EquipCursorItem` 直接戴目标装备**，而不是指望 Outfitter 的缓存/清单逻辑——后者在连续快速换装下极易因缓存陈旧而静默漏换槽位。

## （续5）BrainwasherPro 切天赋卡顿优化（删 3 遍重载）
- 用户反馈：BrainwasherPro 切天赋时 Outfitter 换装 + ActionBarProfiles 切动作条同时触发，非常卡。
- 根因分析（已读 ActionBarProfiles.lua / OneBag.lua 确认）：
  1. **动作条被完整重载 3 次**（最大头）：`CheckAndSwitchActionBar` 里 `maxAttempts=3`，每次切天赋调 `ABP_LoadProfile` 三次（日志 `(1/3)(2/3)(3/3)`）。`ABP_LoadProfile` 一次就扫全法术书(~300 GetSpellName)+19 装备槽+所有背包，再对 **144 槽**逐個 Pickup+PlaceAction，三遍≈432 次光标操作+3 遍全量扫描，且每次同步卡一帧。
  2. 144 槽挤在一帧同步塞满，单次也是一次明显卡顿（需用 OneBag 的帧预算分批才能根治）。
  3. Outfitter 与 ABP 都用同一游戏光标，切天赋时几乎同时触发互相踩踏（很可能正是当初加 3 遍重试想掩盖的毛病）。
  - OneBag 真正手法是**帧预算分批调度器**（`QueueWork`/`ProcessWithBudget`，OneBag.lua:59-125）：每帧只在 100ms 预算内处理一批，超预算 yield 到下一帧，配 `buttonFrame:Hide()/Show()`。核心是分批，隐藏只是顺带消闪烁。
- 本轮按用户选择**仅做第一步（最小改动，不动 ActionBarProfiles 内部结构）**：
  - 删除 `maxAttempts/loadAttempts/currentLoadingSpec/loadCheckTime` 整套 3 遍重试机制。
  - 改为**加载 1 次** + 0.5s 后**延迟补 1 次**（`pendingBarReload` 待办，在 OnUpdate 顶部、节流判断之前触发），规避与 Outfitter 抢光标时个别槽位丢失；补加载不再 3 遍，砍掉约 66% 动作条开销。
  - 保留 Flyout 更新、保留 Outfitter 联动；动作条加载成功提示不再带 `(x/3)`，新增黄色 `[洗脑器] 动作条 'X' 延迟补加载一次（确保完整）`。
- 备份：BrainwasherPro/backup/BrainwasherPro.lua.20260826_233000。
- 待办（用户暂未选）：若仍觉单次 144 槽同步加载有轻微卡顿，可做第二步——移植 OneBag 帧预算分批 + 批量期隐藏/显示动作条，并给 ActionBarProfiles 加 `ABP_LoadProfileBatched` 入口。

## （续6）动作条配置重复加载刷屏（"配置文件 X 已加载"×N）
- 用户反馈：切天赋后聊天框反复刷"配置文件 "防御" 已加载."十几条，实际加载 OK。
- 根因：ActionBarProfiles.lua:285 `ABP_Msg('配置文件 "X" 已加载.')` 是 `ABP_LoadProfile` 内部每次调用都打印的。而 BrainwasherPro 的 `CheckAndSwitchActionBar` 依赖 `lastLoadedSpecName` 去重，但 `OnTalentLoadComplete`（BrainwasherPro.lua:360）在用户确认切天赋(OnAccept)时把 `lastLoadedSpecName = nil`，意图"允许重新检测加载"。切天赋过程若此重置被反复触发（洗脑装置对话在天赋切换时刷新/二次确认），去重被反复清空 → `ABP_LoadProfile` 被一遍遍调用 → 反复打印。
- 修复（BrainwasherPro.lua）：新增**同一 spec 的最小重加载冷却**，无论去重变量怎么被重置，3 秒内绝不为同一 spec 重复加载：
  - 新增 `local lastSpecLoadAt = {}` 与 `ABP_SPEC_RELOAD_COOLDOWN = 3`（秒）。
  - 加载判断（原 `currentSpecName ~= lastLoadedSpecName`）增加：`and (not lastSpecLoadAt[name] or currentTime - lastSpecLoadAt[name] > 3)`。
  - 首遍加载（ABP_LoadProfile 后）与 0.5s 补加载（pendingBarReload 分支）都记录 `lastSpecLoadAt[name] = currentTime`。
  - 效果：切一次天赋最多 2 条"配置文件 X 已加载"（首遍+补1次），刷屏消除；真正隔几秒切回同一天赋仍需重新加载时，冷却已过，正常加载。
- 备份：BrainwasherPro/backup/BrainwasherPro.lua.20260826_234200。
