## Perotharn 护盾条不显示（已修，真凶=竖行条全局拦截）
- 现象：噩梦吸收护盾条不再显示。
- **真凶（用户猜中）**：09-15 加竖行条时，`Plugins\Bars.lua` `BigWigs_StartBar`（~637 行）加了全局拦截——VerticalBars 启用时原版计时条一律 return（只豁免带 target 的 MonitorBar）。而 HP 护盾条（`BigWigs_StartHPBar`）正是通过 `BigWigsBars:BigWigs_StartBar(..., false)` 直接方法调用建条的，target=nil → 被拦截，盾条创建前就被吞掉。竖行条自身也收不到盾条（HP 条不走 BigWigs_StartBar 事件），所以两边都不显示。
- Perotharn.lua 的 trigger 收窄（「佩罗萨恩获得了噩梦吸收的效果」→「噩梦吸收」，enUS→「Nightmarish Absorption」）属于顺带的健壮化加固，保留（整句 trigger 是已踩三次的老坑）。
- 修法（Bars.lua 两处）：① `BigWigs_StartBar` 签名末尾加 `force` 参数，拦截条件改为 `not target and not force`；② `BigWigs_StartHPBar` 调用处追加 `false, nil, nil, true`（emphasize=false, target=nil, spell=nil, force=true）。盾条是暂停的吸收进度条、非倒计时，保持只走原版条显示，不进竖行条时间轴——语义正确。
- 备份：`backup\Bars.lua.20260918_2345.bak`——**注意是改完后备份的**（顺序失误）；回滚=把 force 参数两处撤掉即可。luaparse SYNTAX OK。
- 经验：Bars.lua 里凡是「直接方法调用 BigWigs_StartBar」的特殊条（HP 条/Counter 条），都会被竖行条全局拦截误伤；排查"某条不显示"时先查这条拦截链。CounterBar（864 行，无 target）目前同样被拦，若日后 counter 条不显示按此修。

## 竖行条等待区顺序反转：剩余短的反而在上（已修）
- 现象（截图）：13s「防护恐惧结界」排在 33s「灵魂之井」上方，剩余越短越靠上，整体反序。
- 根因（`Plugins\VerticalBars.lua` 等待区循环 ~505 行）：`waiting` 按 endTime 升序，循环却写 `for i = table.getn(waiting), 1, -1`（先处理剩余最长者），而防重叠钳制 `if y < prevY + minGap then y = prevY + minGap`（WoW 坐标 y 越大越靠上）语义是"后处理的排在前一个上方"——只适配 1→n 迭代。方向反了之后钳制几乎对每个图标都触发，把剩余短的逐个强推到剩余长的上方 → 反序。
- 修法：循环改回 `for i = 1, table.getn(waiting) do`，钳制不动；最先到期者占最靠下自然位置，剩余更长者在上方、太挤时才被上推。已在循环前加注释说明方向约束，防止回归。
- 数值验证（trackH=300/iconSize=32）：TimeToY(13)=-137.5（下）、TimeToY(33)=-54.2（上），1→n 迭代钳制不触发，间距 83px 正确。
- 备份：`backup\VerticalBars.lua.20260918_2348.bak`（这次先备份后改）。luaparse SYNTAX OK。
- 通用教训：**WoW y 轴向上为正**；凡是"必须排在 X 上方/下方 + 最小间距"的钳制，方向必须和迭代顺序（按时间升序/降序）配套，写反就整体反转且无报错。
