## 21:26 buyemall 报错修复：stackSize 是字符串

**报错**：`buyemall.lua:188: attempt to perform arithmetic on local 'stackSize' (a string value)`。

**根因**：初版 `GetItemInfoSafe` 走 env 里的 `GetItemInfo`（= pfUI compat 垫片，重排为 8 返回值），再按固定位置解构取"堆叠"。实测拿到的是**子类型字符串** ⇒ 本客户端原生 `_G.GetItemInfo` 实为**带 reqLevel 的标准 1.12 布局**（[7]=subtype、[8]=stackCount），**证伪了用户级记忆里"少 reqLevel 整体前移"的旧结论**（已更正 `~/.workbuddy/MEMORY.md`）。垫片本身取原生 [5][6][7] 当 type/subtype/stack，在标准布局下 [7]=subtype ⇒ 谁信垫片谁拿到字符串。

**修复**（buyemall.lua）：
1. `GetItemInfoSafe` 重写：**绕开垫片直接 `pcall(_G.GetItemInfo, ...)`**（三形态重试：原链接→数字 ID→item:ID:0:0:0），按"数字落在哪一位"自适应：`v7` 为 number ⇒ 无 reqLevel 布局（子类型 v6/堆叠 v7）；`v8` 为 number ⇒ 标准布局（子类型 v7/堆叠 v8）。删除中间层 `GetItemSubtypeAndStack`，两处调用点直接用 GetItemInfoSafe（返回 itemID,name,子类型,堆叠 四元组）。
2. 连带修复：`IsSpecialBagItem` 里 itemID(数字) 与 gfind 捕获(字符串) 恒不相等 ⇒ 统一 `tonumber(curID)` 再比（草药包/附魔袋检测之前必失效）；物品名匹配 `string.find(link,"["..name.."]",1,true)` 纯文本查找（防名称含模式字符）。

**校验**：check_lua5 SYNTAX OK；chunk upvalue 0；grep 复验：GetItemInfoSafe 仅 1 处定义、GetItemSubtypeAndStack 无残留、`_G.GetItemInfo` 3 处均在 pcall 内。

**教训**：⚠️ 位置式解构 GetItemInfo 返回值在本客户端+pfUI 垫片组合下不可靠；唯一稳法是"按类型特征定位"（数字位=堆叠、非 Interface/INVTYPE 串=子类型）。若发现 pfUI 自身 bags/tooltip 等模块按垫片序取 subtype 出现错乱，根因同此。

## 21:49 buyemall 少买 bug：未满堆叠吞数量

**现象**：买 100 瓶水晶瓶只到手 90（差 10 = 半组）。

**根因**：1.12 客户端 `BuyMerchantItem(index, N)` 在背包存在该物品的未满堆叠时，只买进**首个未满堆叠的剩余空间**，多出来的直接吞掉（实测：背包有 10/20 的水晶瓶，第一笔买 20 只到手 10，之后 4×20=80 ⇒ 合计 90）。原版 BuyEmAll 同样没处理这个 quirk。

**修复**（buyemall.lua，备份 `buyemall.lua.<ts>.partialstack.bak`）：
1. `FreeBagSpace` 增加第 4 个返回值 `partialSpaces`（table，按背包 0→4/槽位顺序记录每个未满堆叠的剩余空间，即客户端填充顺序）。
2. Shift 点击钩子把 `st.partialSpaces` 存入会话状态。
3. `DoPurchase` preset==1 分支重写：先逐个精确填满未满堆叠（每次购买量 ≤ 目标堆叠剩余空间 ⇒ 无论客户端是"只买进剩余空间"还是"跨堆叠分发"都不会丢数量），剩余部分再按整堆叠 + 零头买（此时已无未满堆叠，任意数量安全）。preset>1（按组出售物品）分支未动，理论上有同类风险但组物品场景罕见。

**校验**：SYNTAX OK；chunk upvalue 0；grep 复验 partialSpaces 三处（收集/返回/消费）齐全。

## 21:56 少买 bug 二次修复：改队列逐帧派发（上一版仍缺）

**现象**：精确填满方案（21:49）实测仍然缺数量。

**新分析**：除"未满堆叠吞数量"外，**同一帧内连发多笔 BuyMerchantItem 本身也可能被客户端吞**（6 笔同帧连发，恰好丢一笔 10 的量）。且原实现还有一个隐患：弹窗 DoPurchase 先 Hide，而 OnUpdate 不在隐藏 frame 上触发。

**重构**（buyemall.lua，备份 `.queue.bak`）：
1. **购买请求泵**：独立无贴图 frame `pfBuyEmAllPump`（保持 Show 状态承载 OnUpdate），每 0.05s 从队列取一笔发 `BuyMerchantItem`；商人窗口关闭则队列作废。
2. **未满堆叠改为逐个买 1 补满**：1 恒 ≤ 任意堆叠剩余空间，不依赖客户端选堆叠的顺序（上一版按扫描顺序整笔买 space，若客户端填充顺序不同仍可能丢）。
3. **队列防覆盖**：DoPurchase 在上一队列未发完时直接 return；queueItem 在入队时捕获（防 st.itemIndex 被后续点击改写）。
4. **诊断日志**：`_G.PFBUYEMALL_LOG`（上限 200 条）记录每笔实际发出的请求；`/run pfBuyEmAllDumpLog()` 打印。再缺时可区分"请求没发出"还是"发了但没到账"。

**校验**：SYNTAX OK；chunk upvalue 0；grep 复验 queue/pump/log 各就位。

## 22:04 队列方案实测通过 ✅

用户确认买 100 瓶不再缺数。根因定论为**两层叠加**：① 未满堆叠吞数量（BuyMerchantItem N > 堆叠剩余空间时多出部分被吞）；② 同帧连发多笔购买请求会丢。修复 = 逐个买 1 补满未满堆叠 + 队列每 0.05s 逐帧派发。诊断工具 `pfBuyEmAllDumpLog()` 保留备用。客户端怪癖已写入用户级长期记忆。
