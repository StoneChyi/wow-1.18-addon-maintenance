## 00:20-00:5x chatcopy：「点复制后所有文字都不可见」——盖层 FontString 没有字体

**用户回传**（00:19 诊断）：`父=pfChatLeft` ✅（渐隐那条已修好），但

**关键推理链（这次是靠排除法收敛的）**：
1. `pcall` 一定转发额外参数 —— 反证：`pcall(BuildOverlay, i, frame)` 若丢参，`"ChatFrameScroll"..nil` 会报错被吞，
   覆盖层一个都建不出来；而诊断里 `覆盖层=…·盖=有/0` 说明 BuildOverlay 全跑完了。
2. 盖层**能看见黑底** ⇒ cover 确实在 EditBox 之上、也确实在渲染 ⇒ 缺的只是**文字**。
3. 文字定位只有四种可能：没填 / 没字体 / 颜色全透明 / 几何为 0。而 `SetText` 那条是 pcall 包裹的（失败静默）。
4. ⇒ 最大嫌疑：**FontString 没有字体 = 什么都不画**（客户端行为：FontString 无字体时渲染为空）。

**根因（高置信）**：上一版盖层只写了
```lua

```

2. 字体**两步走、顺序与 EditBox 一致**：`SetFontObject(ChatFontNormal)` → 再 `SetFont`；

7. 诊断加强：`盖=有/N字/字号S/lvlL>框B/bgαA`；`/pfchatcopy` 现在**先强制重填**再测（否则关着复制模式全是 0 字）；

## 性能复核：本日 buff 改动对性能的影响（用户提问，静态测算，未改代码）

**结论**：新增开销全部落在**事件驱动**路径上，**没有新增任何每帧（OnUpdate）工作**；且比改前的 tooltip 猜测路径**更省或同级**。
真正的隐患是"**同一轮刷新里对同一 guid 重复取数组**"——可压 32×，属可优化项而非回归。

**热路径清点**（都是 aura 变化事件触发，非轮询）：
- `RefreshUnit(unit,"aura")`（`UNIT_AURA` / `PLAYER_TARGET_CHANGED` 等）→ `DetectBuff` 循环 `bufflimit=32`；
  `DetectBuff` 现在**自己先取一次** `GetUnitField(guid,"aura")` 判空，再调 `GetBuffSlot`（**又取一次**）→ **每槽 2 次数组构造**。
- `RefreshUnit` 末尾 `component=="aura"` 段 → 目标分离区开启时 `OnTargetAuraRefresh` → `RefreshTargetSepBuffs("HELPFUL")`
  循环 `1..32` **无 break**（空洞机制决定）→ 32 次 `GetBuffSlot`。
- `buff_indicator`（3102）/`custom_indicator`（3159）/`missing_buffs`（3239）三处 `for i=1,32` 也各要 32 次。
- `BuffOnEnter` / 监控区 OnEnter → `GetBuffDisplayIndex`（内部先 `GetBuffSlot` 再 `1..slot` 逐槽 `IsAuraHidden`）：**仅鼠标悬停**，可忽略。

**单次 `GetBuffSlot` 的调用量**：`GetUnitGUID` + `GetUnitField(guid,"aura")`；空槽在此就 return ⇒ 空槽只 1 次数组构造；
命中才继续 `IsAuraHidden` + `GetSpellRecField(name)` + `GetSpellIcon`(有 iconCache) + `GetUnitField(guid,"auraApplications")`
+ `GetSpellRecField(dispel)` + `GetBestAuraCast`(纯 hash 查，很轻)。
→ 目标带 3 个 buff 时一轮 `RefreshUnit("aura")` ≈ 64 次 aura 数组构造（DetectBuff 冗余占一半）+ 32 次 `GetUnitGUID`；
开分离区再 +32。合计量级 ~100 次 DLL 调用 / 次光环变化，**目测 0.1–1ms 级**，战斗中每秒几次事件 → 可忽略。

**为什么不是回归**：改前非玩家单位走的是 `scanner:SetUnitBuff` + `Line(1)`（**每次一次 C 侧 tooltip 布局**），
