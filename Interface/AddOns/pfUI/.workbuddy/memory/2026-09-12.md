## chatcopy：新建聊天窗口（世界）复制层无文字
- 备份：backup/chatcopy.lua.20260912_183154.bak；校验 check_lua.js [OK]。
- 症状：复制模式下 综合/战斗记录 正常显示复制文本，客户端"新建"的 世界 窗口复制时看不到文字。
- 证据（截图像素分析，.workbuddy/chat_lum.py）：世界窗口体区亮度 max=15/255（median 3，全像素 0-15），
  而标签栏 max=214、综合窗口体区 max=255 → 该窗口整体处于 ~5% 显示强度（父窗口 alpha 过低，
  或覆盖层黑底 .95 之下是无文字的空白 EditBox）。另：综合窗口复制层内**无时间戳**、世界窗口有
  → 说明复制层历史由 chatcopy 自己的 AddMessage 包装记录（外层），世界窗口那份没进/没填。
- 结构根因（老实现在 modules/chatcopy.lua）：
  ① 覆盖层 + AddMessage 记录器只在 PLAYER_ENTERING_WORLD 一次性按 `for i=1,_G.NUM_CHAT_WINDOWS`
     建立；循环内 `local name = frame:GetName()` 对 nil 无保护 → 任一窗口不存在/报错即**整轮中断**，
     后面的窗口（含新建的）永远拿不到覆盖层与记录器 → 与"1、2 正常、新建窗口空白"完全吻合；
     切换复制模式的循环同样 `local scroll = frame.scroll` 直接取字段，无 nil 保护。
  ② 文本只在 scroll 的 OnShow 里灌入；窗口隐藏时 Show() 不一定触发 OnShow → 空框。
  ③ 覆盖层是 ChatFrame 的**子对象**，父窗口被 pfUI 渐隐(config chat.global.fadeout=1/fadetime=30)或
     客户端消息渐隐降到 alpha<1 时，覆盖层文字一起变暗直到"看不见"。
- 改动（重写 modules/chatcopy.lua，保持原有观感/按钮渐隐/右建 ChatMenu/UIColor 不变）：
  1. MAX_WINDOWS=20 硬上限扫描，不再依赖 NUM_CHAT_WINDOWS；每窗口单独 pcall（一处失败不影响其它窗口）；
  2. EnsureOverlay(i) 幂等懒创建：按需补建覆盖层 + 按需装 AddMessage 记录器（同一 frame 只装一次，
     记录在 recorderFor[i]，frame 被客户端重建会自动重建覆盖层）；失败可用 /pfchatcopy 诊断；
  3. 记录器/覆盖层分离，历史按窗口号存（histories[i]），覆盖层重建不丢历史；
  4. 切换复制模式 = SetState(on)：进入时 EnsureAll()（把新建窗口补进来）→ 逐窗口显式 pfCopyFill()
     （不依赖 OnShow）→ UIFrameFadeRemoveFrame + frame:SetAlpha(1) + SetFading(false) 压掉渐隐；
     退出时按 pfUI 规则恢复（选中=1、其余=0.5，并按 config.fadeout 还原 SetFading/SetTimeVisible）；
  5. 事件不再 UnregisterAllEvents：每次 PLAYER_ENTERING_WORLD 都 EnsureAll；另外登录后 5 轮 ×0.5s 的
     补偿扫描（客户端/其它插件可能在登录后才补建窗口）；复制模式开启期间每 0.5s 把窗口 alpha 拉回 1；
  6. 包装 _G.FCF_OpenNewWindow：客户端"新建窗口"后立即补建覆盖层并同步复制状态；
  7. 新增诊断命令 `/pfchatcopy`：逐窗口打印 记录器/覆盖层/历史条数/alpha + NUM_CHAT_WINDOWS。

## 事故：nameplates 姓名板全失效（upvalue 超限）+ 校验工具升级
- 症状：进游戏后姓名板整体消失，游戏内**无任何红字/提示**。
- 根因（`Logs/FrameXML.log` 第 41 行）：
  `Interface\AddOns\pfUI\modules\nameplates.lua:2294: too many upvalues (limit=32) near '('`
  → 上面那次改动新增的 **2 个顶层 local**（customNPCColors / customNPCDefault）让
  `OnDataChanged` 及其深层闭包各 +1 upvalue，越过 Lua 5.0 的 32 上限 → **整份 nameplates.lua 不加载**。
  check_lua.js 第四层旧启发式（函数内 local 合并成一个集合 + 只数直接引用）对此**完全漏报**（报 [OK]）。
- 修复（目标：**净增 0 upvalue**）：两张表改挂到**已被 OnDataChanged 捕获的** `unitcolors` 表上——
  `unitcolors._custom`（nameLower -> {r,g,b,a}）、`unitcolors._customdef`（统一色）；
  引用集与改动前完全一致。已确认全库无 `pairs(unitcolors)` 遍历，新增字段安全。
- 新增工具 `.workbuddy/check_upvalues.js`（可 CLI 亦可 require）：按 Lua 语义逐语句维护作用域栈
  （**变量实例化**，同名不同块分开算）+ 自底向上传播**传递 upvalue** + 正确处理 luaparse 把
  `local function f()` 解析成 `isLocal:true` FunctionDeclaration 的情形。SAFE_LIMIT=27（保守）。
  参数 `--detail` / `--unresolved` / `--top N`。
- `check_lua.js` 第四层已替换为该算法（删掉 88 行旧启发式），只提示、不计入 exit code。
- 验证（关键两步）：
  ① **敏感度** —— 构造"爆炸版"（把表改回 2 个顶层 local）：OnDataChanged 27→28，差值被准确捕获；
  ② **等价性** —— `backup/nameplates.lua.20260912_203738.npccolor.bak`（改动前正常版本）与修复版
     逐函数数值**完全一致**（Top12 全对齐，OnDataChanged 均为 27）→ 与"能正常加载的版本"等价。
- ⚠️ 工具数值**系统性低估**：分析 27 ≈ 客户端已贴 32（再 +1 就爆）。所以判定标准是
  "**同一函数前后数值不上升**"，不要拿 32 当安全线。当前 libdebuff 最高 30（同样贴线）。
- 教训：nameplates.lua / libdebuff.lua 这类大文件的核心闭包常年贴着 32 ——
  以后往这些闭包加东西，一律**挂已有表字段**，绝不新增顶层 local。

```lua
  local mov, cand = m1, c1
  if j == 2 then mov, cand = m2, c2 elseif j == 3 then mov, cand = m3, c3 end
```

只遍历 **3 个对角组合**（left↔left、cx↔cx、right↔right；Y 轴 bottom↔bottom、cy↔cy、top↔top），
**没有 top↔bottom / bottom↔top**（Y）、**left↔right / right↔left**（X）这种「边贴边」候选。
所以两条动作条上下紧挨、左右拼接时**根本吸不住** —— 与吸附距离、存档、开关都无关。

复现（仿真场景 15 ②）：bar1 (100, bottom 800, 384×36)、bar2 bottom 770（top 806，距 bar1 下沿 6px）
→ `SnapFind` 返回 `sy=nil`，bar2 不动；`SnapAxis(770, 788, 806, "bottom","cy","top", 8)` 直接返回 `nil`。

**修复**：候选扩到 5 种（`for c = 1, 5` + if/elseif 展开，**不用临时表**，避免拖动期间每帧每目标建表造成 GC 抖动）：

| # | 语义 | X 轴 | Y 轴 |
| --- | --- | --- | --- |
| ① | 同位 | left↔left | bottom↔bottom |
| ② | 同位 | cx↔cx | cy↔cy |
| ③ | 同位 | right↔right | top↔top |
| ④ | 相邻 | left↔**目标 right** | bottom↔**目标 top** |
| ⑤ | 相邻 | right↔**目标 left** | top↔**目标 bottom** |

（mover 坐标 m1/m2/m3 分别代表 起点/中点/终点，与目标键 k1/k2/k3 一一对应；④=m1↔c3，⑤=m3↔c1。）
