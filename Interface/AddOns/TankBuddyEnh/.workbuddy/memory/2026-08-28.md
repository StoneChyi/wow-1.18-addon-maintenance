## 战士招架/躲闪广播最后一公里修复

### 根因
warrior「招架/躲闪」标签页虽然在 `TB_Tabs` 末尾已加、`TB_defaultText[TB_GUI_WarriorPD]` 中文/英文都有、事件注册 / 战士分支判定都已就位，但插件初始化只对圣骑士 `HolyStrike` / `HandOfReckoning` 默认开启 Yell 频道，新加的 `WarriorPD` 标签页所有 Raid/Party/Alone 组下的频道格子全为 nil，所以 `TB_Announce` 里 `Announcements[TBAbility][TB_grp][TB_Channels[i][2]]` 永远 false，从未真正发出过消息。

### 第一轮修复（行 489 后新增，491-502）
参照 Paladin 模式（479-489），新增 Warrior 分支：遍历标签到 `TB_GUI_WarriorPD` 时给 `Raid`/`Party`/`Alone` 三组的 `Yell` 默认写 1。这样标签页**默认开启 Yell**，下次 reload 后生效。

### 第二轮修复（行 748-762 新增 fallback）
用户 reload 后仍说"不通报"。怀疑：游戏内 `/reload` 与完整退出重进对 `VARIABLES_LOADED` 触发不可靠，导致初始化循环没跑。即便第一轮逻辑正确，只要 `Announcements[WarriorPD]` 下任何频道格子都不是 true，for 循环就永远空跑。

加 fallback 到 `TB_Announce` 里：

```lua
if (TBAbility == TB_GUI_WarriorPD) then
    local anyChecked = 0;
    for k = 1, getn(TB_Channels), 1 do
        if (TBSettings[TBSettingsCharRealm].Announcements[TBAbility][TB_grp] and
            TBSettings[TBSettingsCharRealm].Announcements[TBAbility][TB_grp][TB_Channels[k][2]]) then
            anyChecked = 1; break;
        end
    end
    if (anyChecked == 0) then
        SendChatMessage(TBText, "YELL");
    end
end
```

放在 for 主循环**之前**。不依赖：SavedVariables 是否初始化、用户是否 reload、是否手动勾频道——只要 COMBAT_MISSES 命中五个技能名 + 招/闪词，就强制 Yell 一次。

### 教训
给 TankBuddyEnh 加新 TBAbility 标签页时：
1. **初始化阶段**必须显式开启至少一个默认频道（沿用 479-489 的 Paladin 模式），这是用户基本体验。
2. **判定广播阶段**若新标签属于"高价值但低频"事件（如招架/躲闪），可在 `TB_Announce` 里加 fallback：所有频道都未勾就强制 Yell，避免因数据未初始化完全失效。

下一次类似改动（新增 TBAbility 标签）：**双管齐下**——既改初始化默认值，也加 TB_Announce 兜底，确保"零配置即生效"。

## 战士招架/躲闪最终修复（真正的根因）

用户 reload + fallback 都加完之后依然不广播。

### 真正的根因
**Lua 的 `string.find` 不支持管道符 `|` 当多模式分隔符**。

```lua
TB_WarriorPDAttacks = "破甲攻击|复仇|英勇打击|盾牌猛击|震荡猛击"
string.find(arg1, TB_WarriorPDAttacks)
```

会把这整串当成**单个普通子串**在 arg1 里查找，但 `"破甲攻击|复仇|..."` 这个完整字符串永远不可能在战斗记录里出现 → 永远返回 nil → 318 行 elseif 永远不命中 → `TBAbility` 永远不会被赋值 `TB_GUI_WarriorPD` → 即使有 fallback 也是在空字符串上报，不发出任何东西。

我之前几轮一直以为是不识别事件、初始化未生效、兜底逻辑有问题——**根本没想到是 string.find 找不到那个完整子串**。骑士/德鲁伊的代码之所以正常，是因为他们写法是：

```lua
string.find(arg1, TB_Maul)        -- 单技能，OK
or string.find(arg1, TB_SavageBite) -- 单技能，OK
```

各自的 `TB_xxx` 是单一字符串。我把多个技能名压成一个 `|` 分隔的字符串再 string.find 是**完全错误的做法**——这是我引入的 bug（不是 TankBuddyEnh 原有 bug）。

### 修复
1. **TankBuddyEnh.lua 行 603-619 新增 `TB_MatchAnySkill(arg, patternList)`** helper：把 `|` 分隔的字符串用 `TB_strsplit` 拆开，循环 `string.find` 任意一项即返回 true。

2. **318 / 380 行**把 `string.find(arg1, TB_WarriorPDAttacks)` 替换为 `TB_MatchAnySkill(arg1, TB_WarriorPDAttacks)`。

3. 保留 `TB_WarriorPDAttacks` 字符串变量不变——localization 形式简洁。

### Dry-run 验证
- arg = "你的盾牌猛击被团队副本训练假人躲闪过去了"
- 旧实现：string.find 返回 -1 (= Lua nil) → **永不命中**
- 新实现：拆开 5 个技能逐一 string.find → "盾牌猛击" 命中 → **True**
- "致死打击"（未在表）→ 正确返回 False

### 教训
**绝不要把多个可匹配子串塞到一个长字符串里再 string.find**——Lua 的 string.find 不是 PCRE 正则，`|` 只是普通字符。多个子串必须写成多次 `string.find(arg, s) ... or string.find(arg, s)`，或用 `TB_MatchAnySkill` 这种 helper 拆分匹配。

下次加"是否匹配任一技能名"的需求时，**默认走 helper 函数**，不要凭直觉拼字符串再 string.find。这次踩坑的就是这步。

## 战士招架/躲闪通告写入具体技能名

用户确认广播已生效，但希望通告里写出被招/闪的具体技能（如"盾牌猛击被招架了"），而非笼统的"我的攻击被招架/躲闪"。

### 改动
1. `TB_MatchAnySkill` 由返回 `true` 改为**返回命中的技能名字符串**（未命中返回 nil）。
2. 两个战士分支（SPELL_SELF_DAMAGE 318、COMBAT_SELF_MISSES 389）命中后，把 `TB_WarriorPDSkill = 命中技能名` 存全局，并据 `arg1` 是否含 `TB_Parry` 设置 `TB_WarriorPDPD`（"招架"/"躲闪"）。
3. `TB_Announce` 新增 `TB_GUI_WarriorPD` 分支：用 `string.gsub` 把通告文案里的 `$skill`→技能名、`$pd`→招/闪词。`$skill`/`$pd` 缺失时兜底为"攻击"/"招闪"（Test 按钮或异常场景不会残留占位符）。
4. `TB_defaultText[TB_GUI_WarriorPD]` 改为 `"我的$skill被$pd了，dps注意！"`（enUS 同步为 `"- My $skill was $pd! -"`）。
5. `VARIABLES_LOADED` 初始化循环后加**一次性迁移**：若已保存的 WarriorPD 文案是旧默认（"我的攻击被招架/躲闪，dps注意！" 或英文旧默认），自动升级为新带占位符版本——否则用户旧 SavedVariables 不会被 `if (not Text)` 覆盖，reload 后仍看不到技能名。

### Dry-run 验证
- 盾牌猛击+招架 → "我的盾牌猛击被招架了，dps注意！"
- 盾牌猛击+躲闪 → "我的盾牌猛击被躲闪了，dps注意！"
- 破甲攻击+招架 → "我的破甲攻击被招架了，dps注意！"
- 复仇+躲闪 → "我的复仇被躲闪了，dps注意！"
- 致死打击（不在表）→ 不命中（符合预期）

### 注意
若用户曾在 `/tb` 手动改过 WarriorPD 文案，迁移不覆盖，需手动加 `$skill`/`$pd` 占位符才能显示技能名。

## 秒数输入框尺寸修正
用户反馈"秒后不再广播招架躲闪"输入框（`TB_EditboxBroadcastDuration`）比旁边复选框明显拉长。

### 根因
XML 244-321 行：EditBox `<Size x="30" y="32"/>` + 3 段 `Interface\ChatFrame\UI-ChatInputBorder-Left/Right` 纹理都是 `y="32"`。而相邻 `OptionsCheckButtonTemplate` 只有 `x="25" y="25"`，视觉上一高一矮很突兀。

### 修复（TankBuddyEnh.xml 244-321）
四处 `y="32"` 统一改为 `y="20"`：
- 行 246 Size 容器
- 行 270 UI-ChatInputBorder-Left（最左）
- 行 283 UI-ChatInputBorder-Right（最右）
- 行 296 UI-ChatInputBorder-Left（中间填充）

修改后秒数框与 CheckButton 视觉高度接近，不会再被一眼看出"特别大"。

### 经验
WoW 1.12 EditBox 用 ChatInputBorder 类拼出来的高度默认就是 32px（输入框全高），若想要更紧凑必须显式给 Size 和每个纹理单独设小高度，不能依赖 Inset 默认值。下次再加数字输入框时直接给 `y="20"`。
