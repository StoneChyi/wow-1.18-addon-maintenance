# pfQuest-turtle 数据修订记录

db 目录是自动生成的。**2026-08-24 起分工改了**：凡是能表达成"某条记录的某个字段是什么"的修订，
一律直接写进 `db/*.lua`，行内带 `手改 <日期>：...` 注释和依据标记；`overwrites.lua` 只留必须写成
代码的三类（删记录的跨表操作、批量清字段的循环、依赖遍历的兜底逻辑）。
注释格式与依据标记的规范见 `.claude/skills/overwrites-comments`。

**升级上游 db 前，先把 db 里所有 `手改` 注释捞出来**——那就是会被覆盖掉的全部人工修订：

```bash
grep -rn '手改 ' pfQuest-turtle/db pfQuest/db
```

2026-08-06 起那几批直接改在 db 里的（砍树数据、掉率全量导入、来源补齐/清理、树木拆分）
早于这条约定，没有 `手改` 前缀，捞的时候要另外留意。

## 2026-09-14 · 2040「地底突袭」的 `[!]` 不显示（又一条 NextQuestInChain 误判成前置）

现象：暴风城矮人区的沉默的舒尼（6579）身上，2040「地底突袭」的可接图钉不画。
走过去对话框照常弹出——服务端根本没拦，是 pfQuest 自己把它藏了。

根因跟 2026-08-30 的 2975「菲拉斯的食人魔」一模一样：`pre = { 2041 }`。
2041「沉默的舒尼」只是把人指过去的面包屑，`pfQuest/toolbox/extractor.lua:1194` 那条

```sql
SELECT entry FROM quest_template WHERE NextQuestInChain = <entry>
```

把任务链展示用的 `NextQuestInChain` 也写进了 `pre`，而服务端只按 `PrevQuestId` 拦。
于是 `QuestFilter`（`pfQuest/database.lua:1730`）看 `pfQuest_history[2041]` 为空就直接
return，图钉整个不画——只要玩家是在装 pfQuest 之前交的 2041，或者换过机器、清过
SavedVariables，就永远看不到这个 `[!]`。

判据：社区库 `quests.prevquest = 0`，且全库没有任何任务的 `abs(nextquest) = 2040`。
玩家实测走过去就能接。[社区库 + 实测]

改动（**两处都要，缺一不可**）：

- `db/quests-turtle.lua` [2040] 删掉 `["pre"] = { 2041 }`，重导上游后按注释重做；
- `overwrites.lua` 加 `pfDB["quests"]["data"][2040]["pre"] = nil`，否则该文件末尾的兜底
  循环会见乌龟层缺 `pre`、从基础库把 `{ 2041 }` 抄回来（2975 栽过这个坑）；
- `tests/run_merge.lua` 加用例 2b，把 786 / 2040 / 2975 / 7141 / 7142 五条「手工删掉的
  `pre`」一起钉住，防的就是上面那个兜底回填。

### 全库逐条核对：另外 98 条一并清掉

同一个判据扫了合并后的 3830 条 `pre`，**99 个任务**（不含上面的 2040）的 `pre` 在社区库里

证据等级：**除 2040 有玩家实测外，其余都是 `[社区库]` + mangos 语义推导**。
`SatisfyQuestPrevChain` 只在"链上前一条正在进行"时拦人、从不要求交过，这是判定

## 2026-09-11 · 二选一任务做掉一条，另一条的 `[!]` 还挂在图上（互斥组不进 QuestFilter）

现象：灰谷林歌神殿的 40801「耐心是关键」（布罗森·铁林发）与 40807「压力是关键」
（星风指挥官发）是二选一，交掉其中一条之后，另一个 NPC 头上的 `[!]` 还在。

**数据没问题**：两条都带 `close = { 40801, 40807 }`，互斥组是完整的。问题在于
**`close` 在整个插件里只有一个消费点**——`patchtable.lua` 里 `complete()` 的递归展开，
而那条路只有手动跑 `/db query`（`.queststatus` 同步）才会触发。`QuestFilter`
（`pfQuest/database.lua:1719`）根本不看 `close`。

写 `pfQuest_history` 的三条路：

| 路径 | 触发 | 展开 close？ |
|---|---|---|
| `pfQuest/quest.lua:221` | 平时交任务，任务离开任务栏 | ❌ 只写交掉的那一个 id |
| `pfQuest/database.lua:2199` | `GetQuestsCompleted()` | 该实现被 `patchtable.lua` 覆盖，乌龟服上是死代码 |
| `patchtable.lua` 的 `complete()` | `/db query` | ✅ |

所以平时打游戏交任务，互斥兄弟一直是"没做过"的状态，图钉照画。

### 改动一：`QuestFilter` 加互斥组检查

在 `patchtable.lua` 里手动包裹 `pfDatabase.QuestFilter`（1.12 的 `hooksecurefunc`
不支持表方法，文件里 `ShowExtendedTooltip` 等几处也是这个写法）：组里任一条在
history 里，本条就隐藏。跳过自己——自己那条由基座的 history 检查管。

按 history 命中即隐藏是安全的：`close` 只由 `ExclusiveGroup > 0` 生成
（`pfQuest/toolbox/extractor.lua:1116`），语义就是"做了组里任一条，其余的都接不到了"；
`ExclusiveGroup < 0` 那种"整组都要做完"的根本不会进 `close`。全库 351 条，组大小
1~9，抽查了圣洁之书、火焰的召唤、工程学专精、灰谷狩猎几组，语义都对得上。

### 改动二：`complete()` 不再沿 `close` 展开

这条链两个分支各 6 环，但 `close` 只挂在两个分支头上，下游 10 条全靠 `pre`。
`complete()` 把互斥兄弟伪造成"已完成"塞进 history，就顺手满足了下游的 `pre`——
**被放弃那条分支的第二环（40802 或 40808）会冒出一个接不到的 `[!]`**。两种选法
症状对称。

那段展开本来就是"`QuestFilter` 不看 `close`"年代的变通，改动一之后只剩坏处，删掉。
副作用：浏览器里互斥兄弟不再显示成"已完成"（它确实没做过），但地图上照样被挡住。

### 结果

| 场景 | 40807 另一头 | 40808 放弃线第二环 |
|---|---|---|
| 改之前·刚交完没同步 | 显示 ❌ | 隐藏 |
| 改之前·跑过 `/db query` | 隐藏 | 显示 ❌ |
| **改之后·两种都** | **隐藏 ✅** | **隐藏 ✅** |

`run_merge.lua` 加了用例 7/8/9（互斥组完整性、不依赖 `/db query` 的隐藏、分叉链两种
history），断言 68 → **114 全过**。两处改动各做了负向对照：摘掉改动一挂 12 条，
摘掉改动二挂 5 条。

**待实测**：桩环境证明不了客户端交任务那一刻 `quest.lua` 到底往 history 写了什么。
进游戏交掉 40801、**先别跑** `/db query`，确认星风指挥官头上的 `[!]` 已经没了；
再跑一次 `/db query`，确认 40808 也没冒出来。

## 2026-09-11 · 抽取脚本推 `pre` 的规则有洞，补齐 25 条任务的前置

起因：海达克西斯公爵（13278）头上常挂着 `!`，7486「英雄的奖赏」实际接不到。

先排除了声望：`pfDatabase:QuestFilter()`（`pfQuest/database.lua:1719`）判可接性只看
`pre / race / class / skill / lvl / min / event` 七项，**没有声望这一项**，全插件也从不调用
`GetFactionInfo`。所以有声望门槛的任务一律会被标成可接——但 7486 不是这个原因，是 `pre` 丢了。

**根因。** `toolbox/extractor.lua:1181-1198` 推 `pre` 只有三条规则：

1. `PrevQuestId != 0`（取绝对值）
2. 反查 `NextQuestId = <entry> AND ExclusiveGroup < 0`
3. 反查 `NextQuestInChain = <entry>`

规则 2 那个 `ExclusiveGroup < 0` 是致命的：上游大量 `NextQuestId` 配的是 `ExclusiveGroup > 0`
（互斥组，做完组里任一条就解锁后续）或者 `ExclusiveGroup = 0`（单条前置），这两种一条都接不住。
6824「敌人之手」→ 7486 就属于后者。

拿社区库 417 条 `nextquest` 非 0 的链接跟 pfQuest 现有的 `pre` 对了一遍（**对的是合并后的值**：
模拟了 `patchtable` 和 `overwrites.lua` 末尾那段七字段兜底回填，只看 db 文件会漏算），
**86 条对不上，归到 31 个 target**。

**这次补了 25 个 target / 61 条链接**，分三类：

- **多变体 → 同一后续**（17 个）：阵营镜像或等级段变体，如 8922/8923「超自然的设备」各挂 8 条
  「热心的建议」、四个瘟疫之锅各挂 A/H 两版、3638/3640/3642「保密协议」挂工程学专精那几条。
  pfQuest 的 `pre` 语义本来就是「任一完成即可」（`database.lua:1730-1740` 的 `one_complete`），
  跟上游 `ExclusiveGroup > 0` 正好同构，补进去零风险。
- **单链**（2 个）：2206 ← 2205、7637 ← 7638，跟 7486 同型。
- **并行前置**（6 个）：target 已有 `pre`，上游还有另一条路通向它（2801、9033、7163、7164、
  7381、7382、80707）。追加只会更宽松，不会造出新的误报。

**顺带修掉一个死锁：8223「更多发光的蝎血」的 `pre` 指向自己**（`{ 8223 }`）。上游
`prevquest = 8223` 是 mangos 表达「重复任务」的写法，规则 1 直接 `math.abs` 当前置用了。
结果在 `QuestFilter` 里两条路都走不通——没做过则 `one_complete` 为 nil 被 return，做过则
先被 `pfQuest_history[id]` 那行挡掉，**这任务永远显示不出来**。改成真正的前置 `{ 8222 }`
（闪光的蝎血）。全库扫过，这种自指只有这一条。

**有意跳过的 6 个 target / 30 条链接**——全是战场重复任务：8114 控制四座基地、8121 夺取四座基地、
8292 功勋奖章、8293 荣誉奖章、8298 / 8300 更多的资源。pfQuest 根本没有 repeatable 概念
（`extractor.lua:1111` 算了 `repeatable` 变量但从没写进 db），这些任务一进 `pfQuest_history`
就被永久隐藏，补 `pre` 收益很低，且图钉都在战场里面。要补随时可以，判据同上。

**落点。** 两层都有的写 `pfQuest-turtle/db/quests-turtle.lua`（16 条），只在基础库的写
`pfQuest/db/quests.lua`（9 条）——写 `data` 会被 `patchtable` 整条冲掉。改完核对过：
25 个 target 没有一个丢掉原有的 `pre` 值，重跑缺口统计只剩上面那 6 个战场 target。

**验证方式换了：不再用 Python 模拟合并，改成真跑。** 新增 `pfQuest-turtle/tests/`
（`run_merge.lua` + 桩环境 `harness_db.lua` + README），按 `.toc` / `init/*.xml` 的顺序

## 2026-09-06 · 木喉隧道两侧的 NPC 各多一个邻图幽灵落点（15395 / 11556）

起因：游戏里指着纳菲恩看不到 8461「北方的死木熊怪」，怀疑是区域数据错了。**确实是区域的

**根因是子区域 1769「木喉隧道」在 `pfQuest/db/zones.lua` 里没有条目。** 上游
`spawn_points` 把这条隧道里的 NPC 全记在 zone 1769 上：

2975 的证据（[社区库]）：`quests.prevquest = 0`，且没有任何任务的 `nextquest` 指向 2975。

## 2026-08-24 · 落点与上游社区库对齐；人工修订从 overwrites 搬进 db

### 一、根因：上游抽取脚本按包围盒选图，再用蒙版剔除

`pfQuest/toolbox/extractor.lua` 的 `GetCreatureCoords` **不看 creature 的 zone_id**，而是
`JOIN WorldMapArea ON x_min < position_x < x_max AND y_min < position_y < y_max`——一个 spawn

1. `if not maps[id] then return true end`——**没有蒙版的分区一律不剔**。`maps/turtle/` 只有
   4 张（1519 / 406 / 45 / 85），北风领(5581) 等乌龟新区全部没有，邻区蹭进来的落点永远保留。
2. `maps/turtle/1519.png` 在**扩图后**的要塞、港口那片 alpha=0（实测 px(80,38)、(83,34)、

分区的变换换算一遍，落点附近 (>0.5 格) 一个都没有**——这个落点指向空处。

## 2026-08-14 · hint 改成语言表的键，不再在数据层写死中文

`summon.hint` 原先直接写成品中文，`overwrites.lua` 里躺着一串中文句子，其它语言的客户端也只能
看中文。改成**语言表的键 + 占位符**：

```lua
hint = "Kill the ghouls to release $target"          -- 数据层只有英文键
["Kill the ghouls to release $target"] = "杀死食尸鬼释放$target",   -- 译文在 locales.lua
```

三个占位符，替换时自动套上与内置四句一致的青色，模板里不必写颜色码：

| 占位符 | 换成 |
|---|---|
| `$source` | 召唤源名 |
| `$item` | 召唤道具名 |
| `$target` | 被召唤者名 |

用命名占位符而不是 `%s`：WoW 的 Lua 支持 `%1$s` 位置参数但桌面 Lua 5.4 不支持，桩环境会挂；
命名占位符两边都能跑，译文里还能随意调换语序。

缺译文时 `pfQuest_Loc` 回落成键本身，所以非中文客户端看到的是通顺的英文而不是中文：

## 2026-08-13 · 用 UnitExists("mouseover") 区分指向的是怪还是场景物

召唤源与被召唤者同名时（41742 的火盆与怪都叫「达格诺斯之焰」），`pfMap.tooltips` 只有
一个键，名字判据分不出鼠标指的是哪一个，原先一律按「指向被召唤者」处理。改为再问一句
`UnitExists("mouseover")`：场景物不是单位，所以「同名且不是单位」即召唤源本体。

```
指向火盆                      指向怪物
[!] 驱逐邪恶                  [!] 驱逐邪恶
- 召唤 达格诺斯之焰            - 达格诺斯之焰: 0/1
```

**`isunit` 只在同名这一种情况下当裁判。** `summon.U` 的召唤源自己也是单位，它分不开，
那种形态必须继续走名字判据；放宽成「是单位就不出召唤行」会把 4642 的三段链打回原形
（变异测试实证：那么改会挂掉 4 条断言）。

调研过 API 归属，`UnitExists` 与 `mouseover` 令牌都是 1.12 原生，不依赖任何 DLL：
五个 DLL 里 `UnitExists` 精确与模糊匹配均为 0；`SuperWoWhook.dll` / `nampower.dll` 只
提供**写**入侧的 `SetMouseoverUnit`（vanilla 缺的是宏里 `@mouseover` 施法）；nampower 自己
的设置项说明把 `'mouseover'` 归为 "In the base game" 的单位标识符，`NP_EnableUnitEventsMouseover`
是给已有的 UNIT_* 事件节流；pfUI 的 tooltip 模块无版本门控地用它；Ace2 期的
`SpecialEvents-Aura-2.0` 也用它且零 DLL 感知。这也推翻了 summon 设计当初立的
「不引入 pfQuest 未曾调用过的游戏 API」硬约束——该约束担心的 1.12/1.17 差异在此不存在。

**待实测**：桩环境只能验「传 true/false 时分支走对」，验不出游戏里指火盆时 `mouseover`
是否真的为空。特别要试「先指怪再指火盆」这个顺序——CleveRoids 的注释提到 mouseover 会
残留旧值（那是写入路径的问题，但顺序相关的读取仍需确认）。另外指向**单位框架**时
mouseover 可能不被设置，同名的 41742 在那种情况下会误显示召唤行；只此一条任务，可接受。

## 2026-08-13 · 召唤源支持单位（summon.U）与「召唤 X」提示行

`summon` 原本只认 `O` 场景物与 `A` 区域标记。有一类召唤是**对着怪用物品**把它变成别的怪，
召唤源是单位，两种键都表达不了。`GetSummonCoords` 补 `U` 分支后可以写：

```lua
pfDB["units"]["data"][9621]["summon"] = { U = 6557 }
```

`U` 与 `O`/`A` 有一处不同必须记住：**场景物是死物，落点就一个；单位有几十个会移动的落点，
等于把整片同类怪都标成目标。** 只在「哪一只都行」时才写 `summon.U`。

配套：`ShowTooltip` 多收一个 `hovered` 参数（`map.lua:220` 那个 GameTooltip 首行文字，
本来就在调用点手边，只是没往下传），指向召唤源本体时改打一行「召唤 X」。召唤源与被召唤者
共用同一个节点表，meta 分不出鼠标指的是哪一个，只能靠名字判。已上线的 40908「黑色华尔兹」
不改数据即刻受益：指向阿利亚坦的篝火显示「- 召唤 柳」。

**召唤信息只走这一条 tooltip 行，不进导航箭头。** 箭头文案（`BuildQuestDescription`）
一概按 `obj` 类型正常显示——击杀链「击杀 X」、拾取链「拾取 X 来自 Y」、对话链「与 X 交谈」，
与普通任务完全一致。原先给召唤加的专用措辞（`Use %s here to summon %s`）连同 `summon.I`
→ `meta.summonitem` 的整条管线一并移除：分支删掉后该字段零消费者，留着就是死代码。
9621 的数据从 `{ U = 6557, I = 12288 }` 简化为 `{ U = 6557 }`，用的是哪件物品在紧邻的
注释里记着。

**召唤源身上不挂目标进度。** 它不掉那件东西、也不是要杀的那只，挂上去是误导。所以
`summonline` 成立时目标循环与兜底分支一并让开，只留任务名 + 召唤行两行；进度归被召唤者
与地图图钉。40908 是这样：

```
阿利亚坦的篝火          柳
[!] 黑色华尔兹          [!] 黑色华尔兹
- 召唤 柳               - 柳: 0/1
```

判据只有 `hovered ~= meta.spawn` 承重（单位与场景物同名的 41742 靠它挡掉）。同时保留的
`meta.spawnalias` 那半今天恒成立、变异测试杀不掉，留作将来多出第三个 tooltip 注册键时的
防线——与 `SearchMobID` 里那个「今天从未生效仍保留」的 `coords` nil 检查同一性质。

### 迁移 4642「融合软泥怪」

`obj.I` 的样本 12291 掉自 9621「巨大的软泥怪」，而 9621 是对 6557「原生软泥怪」使用
12288「堕落软泥怪」变出来的，没有落点。原先在 `overwrites.lua` 里硬塞 `obj.U = { 6557 }`
绕过——图钉是有了，但文案成了「击杀原生软泥怪」，杀它根本拿不到样本。本次删掉该行改用
`summon`，图钉数不变（27 个），指引改对：

```
原生软泥怪                        巨大的软泥怪 / 地图图钉
[!] 融合软泥怪                    [!] 融合软泥怪
- 召唤 巨大的软泥怪                - 融合的软泥怪样本: 0/1 [100%]
```

原注释把所用道具写成了 12291（实为 12288），一并订正。9621 只在基础库，所以写 `data`

## 2026-08-13 · 召唤类任务目标（units.summon）

被召唤出来的目标怪物在服务端没有 `spawn_points`，`coords` 是空表，pfQuest 画不出目标
图钉、鼠标指向也没有任何任务信息。全库有 218 条任务的 obj 全部指向这类无坐标单位。

根因在 `SearchMobID`：`obj.U`（击杀）/ `obj.I`（拾取）/ `obj.T`（对话）/ `obj.IR`（用物品）
四条链路最终都汇入它，它按单位自己的 `coords` 逐点调 `AddNode`，空表则循环零次——图钉
与鼠标提示（在 `AddNode` 里逐点注册）一起没有。堵在这一点，四条链路全断。

单位新增 `summon` 字段声明召唤来源，`SearchMobID` 在无落点时据此解析坐标：

```lua
pfDB["units"]["data-turtle"][62585]["summon"] = { O = 2020193 }        -- 场景物召唤
pfDB["units"]["data-turtle"][80123]["summon"] = { A = 900010, I = 42371 }  -- 坐标处用物品召唤
```

键沿用 pfQuest 既有类型字母（`O` 场景物、`A` 区域标记、`I` 所需物品），不用正负号分流。
（`I` 后来被移除，见上方 2026-08-13「召唤源支持单位」一条。）
改这一处四条链路一起恢复——三段链（召唤→击杀→拾取物品）无需任何额外代码即自动可用。

配套改动：`AddNode` 支持 `meta.spawnalias`，使鼠标指向召唤源本体（如那堆篝火）也显示
任务信息；`patchtable` 对老引擎降级——
无能力标志 `pfDatabase.summonobjectives` 时把召唤源坐标直接复制进 `coords`，图钉不丢。

已迁移两条：41742「驱逐邪恶」(62585 → 2020193，两者同名)、40908「黑色华尔兹」
(61514 → 2020026「阿利亚坦的篝火」，与「柳」不同名)。后者原先借用篝火坐标硬编码在
`overwrites.lua`，本次删除。

**已知限制**：召唤坐标只在 `SearchMobID` 内部解析，未回写 `units[id].coords`，所以
`browser.lua` / `slashcmd.lua` 里直读 `coords` 的地方看不到召唤单位：点开后的位置分区为空、
主动加地图筛选时被滤掉、不出现在「本区域 N 级怪」清单。**按名字搜索不受影响**
（`BrowserSearch` 只匹配名字表），地图图钉也不受影响。影响随每新增一条 summon 线性增长；
若要消除，需把 alias 解析与 coords 判空解耦后在加载期回写坐标——注意不能只回写坐标，
那会让 `summon` 分支永不触发、别名提示失效。

开发期用了一套桌面 Lua 桩环境（加载真实 `database.lua` / `map.lua` 跑断言，`run.lua`
41 条、`run_legacy.lua` 6 条）。它**不进版本库**——pfQuest 是 vendored 的上游插件，
塞测试目录进去会在升级上游时碍事，故 `pfQuest/tests/` 已列入 `.gitignore`，只在本地留存。
开发中三次发现「断言名字说在测某事、实际结构测不到」（同名数据致恒真、缺 obj.IR 覆盖、
假的 meta 复用+子串检查），均靠变异测试暴露——改这批代码时建议沿用该手法验伤。

### 二、精度统一

小数位超过 3 位的一律**向上**取整到 3 位（`0.0001` → `0.001`）。向上是为了不归零：
`database.lua` 对物件掉落有 `chance > 0` 判断，舍成 0 会让图钉直接消失。

| 项 | 数量 |
|---|---|
| 触发取整 | 90739 |
| 最终落盘改写 | 98211 |

pfQuest 显示掉率是裸字符串拼接（`map.lua` 三处），1.12 的 Lua 把数字按 `%.14g` 转换，
不做四舍五入。上游有 192 个取值是 1/3、1/6 这类除不尽的小数，不取整会在 tooltip 里
铺开 14 位（`16.666666666667%`）。

### 三、清理 overwrites

db 里已是上游值后，`overwrites.lua` 里 73 条掉率覆盖写的是同一个数，删掉不改变任何结果
（逐组验证过：运行时 373970 组来源数据前后完全一致）。保留 13 条——9 条是 db 里根本
没有的来源（按任务文本推的），4 条掉率与 db 不同。

判据是「删掉后合并结果是否不变」而不是「与上游是否一致」：`overwrites` 写的是整表替换，
删掉后生效的是 db 自己的表，所以来源集合和掉率值都得对上。

### 四、`U`/`O` 的效果

以导入前可比的 305425 组「物品→来源」为基准：

|---|---|---|

所以下面第六节换了基准重新统计，两个数字不能直接比。

### 五、`R` 引用掉落表：按上游掉率重新分组

`R` 是共享掉落表的引用，是个存储压缩机制：一群怪共用一份战利品时，名单在 `refloot`
里只存一份，物品侧只写「属于第几号表 + 掉率」。10429 条 `R` 表示了 178 万组
「物品→来源」，压缩约 171 倍——对要塞进 1.12 客户端的库来说这个结构是必须的。

代价是**一个 `R` 条目只有一个掉率，套用到该表的全部来源**。而上游的掉率是
`A(来源引用该表的概率) × B(物品在表内的概率)`，`A` 因怪而异，一个值表示不了。
`亚历山大领主的战斧` 原本一个值，实际是普通骷髅 0.001%、佐拉巨像 9.091%。

解法是按上游掉率把来源重新分组。关键性质：既然掉率是两个因子的乘积，按 `A` 分组的
划分**与物品无关**，一次切分对所有引用该表的物品同时成立。实测验证了这点——重构后
所有 `(物品, 子表)` 组合掉率唯一，零例外。

| | 重构前 | 重构后 |
|---|---|---|
| 引用表 | 684 张 | 762 张 |
| `R` 条目 | 10429 | 11958 |
| `refloot-turtle.lua` | 36312 行 | 37129 行 |

66 张表被拆开，新增 144 张子表（ID `900001-900144`，避开提取器 ID 段）。其中 51 张
原地改写，15 张原本只在基础库，转写进 turtle 层才能覆盖。另有 466 张表组内掉率本来
就统一，无需拆分。

**来源集合完全守恒**：展开后 2118993 组「物品→来源」，丢失 0、新增 0，只有 139387 个
掉率变准。上游无值的子表条目沿用该物品对原表的旧掉率——不这么做这批来源会整个丢失。

很大一部分原值是 `0`：社区库里引用表内部**分组**的物品，`ChanceOrQuestChance` 本身
就是 0（组内随机选一个），提取器照抄了。`0 >= minChance` 恒为假，所以这些条目从来不出
图钉，问题一直没被发现。例如 `命运 (647)` 掉自佐拉巨像，上游 68.36%，本地记的是 0。
